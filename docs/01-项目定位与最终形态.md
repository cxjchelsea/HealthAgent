# HealthAgent — 01 项目定位与最终形态

## V4.2 命名与追踪说明

统一使用语义名称标识组件、领域、实验和八大智能；开发阶段使用 S0–S8；正式测试案例使用 T-001 格式。规范见 `../README.md` 和 `../traceability.json`。

## 1. 执行摘要

HealthAgent 是个人独立研发的**面向长期任务的通用自主 Agent 应用**。系统以个人健康、健康教育、结构化数据、报告、生活方式管理、情感支持及健康商品辅助作为主要业务试验场，但**医学不是核心技术边界**：通用 Agent 层应能够在不修改主执行机制的条件下替换为其他领域能力。

项目以三个可证明的能力为中心：

1. **自主行动**：用户表达目标后，Agent 能根据上下文与可用能力选择下一步操作，执行工具、检查结果、必要时澄清或修订计划，而不只生成一段回答。
2. **连续可靠**：跨轮次、跨会话、跨工具工作时，能够保持正确事实与任务状态；外部失败或输入更正后，可安全继续，权限和高风险动作有确定性约束。
3. **可度量改进**：为执行轨迹、任务结果、错误归因、上下文/记忆策略和 Harness 配置建立可复现实验；能够说明技术决策是否带来真实收益。

本项目的主要受众包括个人演示用户、技术面试官与开源代码阅读者。它是求职作品，不是未经临床验证的诊疗产品。

### 1.1 一句话定义

> 用户通过一个统一工作台表达目标，由一个主 Agent 协调模型、工具、知识、用户数据与受约束的业务能力，持续推进可观察、可暂停、可恢复、可验证的任务。

### 1.2 成功的外显证据

- 真实运行的 Web 应用，而不只有架构图和 Prompt。
- 一条**非健康领域**通用任务和至少两条**跨健康领域**任务能完整端到端执行。
- 支持真实的工具输入/输出、执行轨迹、受控写操作、错误恢复与用户修正。
- 健康数据与医学知识有来源、时间、版本和适用边界。
- 有可复现 Benchmark、Baseline、消融实验和失败案例分析。
- 能清晰解释 Framework、Runtime、Harness、Skills、Tools、MCP、Memory、Context 的职责差别，且代码结构与解释一致。

## 2. 项目背景与动机

### 2.1 解决的产品问题

传统软件以模块为入口：用户必须知道问题属于“体检、健康档案、慢病、监测、科普还是商品”。通用聊天机器人虽然能回答问题，却通常缺乏对真实数据与外部系统的执行权、长期状态以及结果校验。

HealthAgent 试图提供新的交互范式：**从菜单驱动转向目标驱动**。用户无需预先识别业务模块；系统理解目标、获取必要数据、选择能力、形成结果，并在用户同意的边界内更新计划或安排后续任务。

### 2.2 解决的工程问题

单轮对话成功不代表 Agent 可用于复杂任务。长期任务会遭遇资料缺失、错误工具、数据冲突、上下文膨胀、用户变更要求、审批等待、任务中断、重复外部执行等问题。项目将这些问题转化为可实现和可测量的工程能力。

### 2.3 求职定位

**主要匹配**：AI Agent 应用工程师、LLM 应用研发、智能体全栈工程师。  
**兼容展示**：Agent 平台/智能体工程化岗位中的工具集成、可观测、执行可靠性与评测。  
**不作为核心定位**：医疗算法研究员、临床诊断系统研发、LLM 预训练或纯强化学习训练岗位。

设计选择首先服务于可交付的 Agent 技术证据，而不是医学领域的功能覆盖率或前沿名词数量。相关招聘趋势与论文调研应放在独立参考资料中，并定期更新，不随市场宣传立即改变项目架构。

## 3. 用户与使用环境

### 3.1 目标用户

| 用户 | 主要目的 | 典型使用方式 | 约束 |
|---|---|---|---|
| 演示体验用户 | 体验跨数据、知识、工具的智能协作 | 对话、上传报告、查看个人趋势、创建目标 | 使用合成或明确授权的数据 |
| 长期健康记录用户（模拟） | 持续记录和回顾指标、习惯和目标 | 定期上传记录、查看变化、调整计划 | 不把系统当作临床诊疗替代 |
| 技术面试官 | 判断 Agent 工程深度与真实性 | 观看实时 Demo、Trace、失败注入、评测结果 | 必须可重复演示、可解释 |
| 开源开发者 | 理解架构并扩展能力 | 本地启动、实现新工具、运行测试 | 文档、配置、数据许可清楚 |

### 3.2 设备与部署假设

- 首选桌面浏览器，兼容响应式页面；移动端原生 App 不列为初期目标。
- 个人电脑可运行 API、数据库、向量检索与前端；主 LLM 默认通过可配置 API 调用。
- 支持本地 Docker Compose 起步；线上公开体验仅使用合成数据与安全的模拟副作用。
- 无真实医院接口、电子处方接口、生产医疗身份体系和药品支付系统依赖。

### 3.3 用户的控制权

用户应能查看系统为何请求某项数据、哪些信息被长期保存、哪些写操作在等待确认、如何取消计划/提醒、怎样更正历史事实。Agent 的主动性必须服从用户授权与确定性安全规则。

## 4. 最终产品形态

最终形态是一个**统一智能工作台 + 可视化健康空间 + 可观察任务系统**。以下是产品目标，不代表需要在第一个版本全部完成。

### 4.1 主工作台（Chat + Task Workspace）

**布局建议**：左侧会话/任务列表；中部对话和结构化结果；右侧任务步骤、证据、可用工具及审批卡片。小屏幕以抽屉折叠。

用户可：

- 自由提出需求，不必先选“健康中心/报告/导购”。
- 在任务期间追加条件、更正数据、提出新目标或终止任务。
- 看到任务状态（准备中、执行中、等待用户、已完成、失败或已取消），而不是只有“模型正在思考”。
- 查看最终产物（分析报告、结构化比较、管理计划、提醒任务）及其来源。
- 对高影响写操作进行审阅、确认或拒绝。

系统不得将模型内部私有推理全文暴露为产品承诺。公开的是**可审计的动作与结果**：工具名称、公开参数摘要、执行状态、依据和用户可理解的计划说明。

### 4.2 个人健康中心（Human-centric Health View）

主要用于**数据可视化与导航**，不是独立决策引擎：

- 人体轮廓/身体系统交互入口：初版优先 2D SVG，3D 为可选增强。
- 指标面板：测量值、单位、测量时间、来源、参考区间（如果适用）和历史趋势。
- 器官或身体系统与指标的映射必须保守：并非每个指标都能归属某个器官，也不能推断器官健康分数。
- 观察数据的缺失、过期、不确定与冲突状态明确展示。
- “问 Agent”可就当前筛选指标发起具备上下文的问答或分析任务。

**示例交互**：用户在“心血管”标签下看到近期血压记录，点击“比较过去三个月”，Agent 调用结构化指标分析工具，再结合可信科普资料解释趋势及局限。

### 4.3 文档与知识空间

- 上传个人有权使用的 PDF、图片或结构化报告。
- 显示解析成功/失败、字段置信度与需人工纠正的信息。
- 对报告进行指标归一、历史对照和来源回溯。
- 健康知识问答必须区分可引用证据与模型一般性生成内容；证据不足时明确告知。
- 知识库按许可、版本、地区和时间维护；不得把原公司内部医学文件直接并入个人公开仓库。

### 4.4 计划、提醒与长期任务中心

- 创建、查看、修改、暂停和删除用户自愿建立的健康生活目标。
- 展示阶段性进展与完成状态，支持新数据触发回顾。
- 由调度/事件服务决定什么时候触发任务，Agent 决定授权范围内如何解释、总结或选择下一步。
- 需要外部通知时，保留单独授权、频率控制、免打扰、幂等与取消能力。

### 4.5 健康商品辅助区

- 搜索健康设备、比较属性、过滤预算和使用限制，展示证据与来源。
- 药品部分仅在有可靠、适用地区的规范信息源及相应校验后，提供**非处方药标签信息查询、候选信息对比与药师转介**；不直接作个人用药决定。
- 不实现真实支付、开方、代购处方药或自动药物推荐转化闭环。
- 不能因个人健康数据触发隐性商业推销；健康信息与商品推荐需用途分离并明确告知。

### 4.6 记忆与隐私控制台

- 展示已存储的用户偏好、长期目标、明确约定。
- 用户可以更正、取消持久化或删除相应记录。
- 明确区分健康事实、个人偏好、模型推测和任务执行状态，不能混成单个“记忆向量库”。
- 支持演示用多用户隔离，避免跨用户混入健康数据。

### 4.7 开发者观察与评测面板

面向求职展示的重要产品组成，而不是仅供后台调试：

- 浏览一次任务的 action/observation 时间线。
- 显示模型版本、工具版本、Prompt/Skill 版本、Token、延迟和失败原因。
- 对比 Baseline 与增强方案的结果，按任务类型筛选。
- 一键复现可公开测试案例与失败案例（避免泄露敏感内容）。

## 5. 产品能力地图与功能边界

### 5.1 通用 Agent 能力

| 功能域 | 用户能看到什么 | 产品层验收证据 | 细节归属 |
|---|---|---|---|
| 通用对话 | 多轮对话、流式输出、理解目标 | 真实模型响应，能够保持轮次语境 | 02/04 |
| 自主任务 | 自动选择工具和下一步 | 非硬编码任务的完整执行轨迹 | 04/06 |
| 规划与修订 | 显示任务目标、步骤和变化 | 目标变化后正确保留/取消动作 | 04/07 |
| 工具与 Skills | 使用本地或外部能力 | 可替换工具及一致的调用记录 | 04 |
| 上下文 | 适用数据进入当前任务 | 不跨人、不跨任务串扰 | 04/08 |
| 长期记忆 | 记住经过授权的偏好和目标 | 旧记忆冲突可更正/不误用 | 04/08 |
| 受控动作 | 审批、取消、权限拒绝 | 拒绝后无副作用 | 03/04 |
| 自我约束 | 识别不可执行请求 | 合理拒绝/转介、不中断合法任务 | 04/08 |
| 评测 | 查看任务正确性和效果变化 | 有可复现数据与失败归因 | 06/07/08 |

### 5.2 领域能力地图

| 能力域 | 代表功能 | 面向主 Agent 的形式 | 实现边界 |
|---|---|---|---|
| 健康知识 | 科普、概念解释、证据查询 | 检索工具/知识集合/Skill | 不自动等同于医疗建议 |
| 个人健康数据 | 健康档案、测量记录、趋势 | 查询与计算工具 | 来源与身份强约束 |
| 体检和报告 | 提取、纠错、比较、解释 | 文档处理与结构化工具 | 未确认字段不可当事实 |
| 长期管理 | 目标、计划、回顾、调整建议 | 有状态任务工具 | 医疗治疗方案非自主修改 |
| 预测/监测 | 时间序列、研究模型、监测事件 | 专业算法/规则工具 | 不声明临床诊断准确性 |
| 情感支持 | 支持性交流、偏好延续、主动问候 | 交互策略/记忆/任务 | 不替代心理治疗、不诱导依赖 |
| 导购 | 健康设备、受限 OTC 信息比较 | 搜索、过滤、约束核验工具 | 无自动购药/处方权 |
| 问诊扩展 | 与 AIdoctor 的受控协作 | 独立能力接口/Handoff | 不绕过其临床边界 |

### 5.3 通用与领域的隔离要求

核心执行器不得包含“血压”“体检”“抗衰”等专有分支逻辑；领域通过描述、Schema、许可的工具、知识集合及规则进入统一能力目录。跨领域任务仍由同一个主 Agent 按合法候选能力进行组合。此项必须通过一个**非医学任务**和一个**新增模拟领域工具**的扩展测试证明。

## 6. 关键用户旅程与目标行为

以下为最终演示故事板。详细用例步骤、异常路径与验收数据在 02 中维护；这里描述用户可观察的产品结果。

### 6.1 Journey A：通用任务（证明 Agent 不依赖医学）

**输入**：比较两份虚构服务方案文件，计算三年总成本并给出带来源的结论。  
**系统行为**：查找文件 → 提取条款 → 调用计算 → 如资料不全则澄清 → 输出证据链接/字段来源。  
**变化注入**：其中一份文件价格字段有冲突，Agent 不应凭空选择，而需标记冲突并请求确认或按约定优先级处理。  
**演示价值**：模型驱动的工具选择、跨文件推理、工具失败/数据冲突处理、可追溯结果。

### 6.2 Journey B：体检到生活目标（跨领域组合）

**输入**：“对比今年和去年的体检记录，找到需要持续关注的变化，帮我做一个下个月的生活习惯追踪计划。”  
**系统行为**：身份限定的健康数据查询 → 体检字段比较 → 趋势计算 → 可信知识检索 → 计划草案 → 等待用户确认 → 安全写入。  
**变化注入**：用户更正某项数据属于他人，原分析受影响部分须失效并重新执行；不能修改另一人的资料。  
**演示价值**：跨领域 Planning、事实来源治理、重规划、审批与状态一致性。

### 6.3 Journey C：跨会话长期管理（证明记忆与执行连续性）

**输入**：用户设定每周回顾运动记录、再在新会话修改目标。  
**系统行为**：保存明确授权的目标 → 定时任务触发 → 查询真实记录 → 生成回顾 → 用户改目标后调整后续任务。  
**变化注入**：任务执行中断或重复触发，系统恢复后不能多建提醒。  
**演示价值**：长期记忆与业务状态区分、事件驱动、Checkpoint、幂等、防重复副作用。

### 6.4 Journey D：情感支持（证明八大智能的交互差异）

**输入**：“今天很烦，不想听方法，只想说说。”  
**系统行为**：理解用户偏好的支持性交流，不擅自调用计划生成或健康评估工具；用户主动改口希望制定小目标时再转入任务模式。  
**变化注入**：之前保留的“喜欢建议”的偏好与本轮明确要求冲突，本轮最新授权应优先。  
**演示价值**：语义理解、情绪理解、隐含需求澄清、对话策略、自我约束与时效性记忆。

### 6.5 Journey E：健康设备导购（证明受约束工具使用）

**输入**：“给家人选一款操作简单、预算有限的家用血压计。”  
**系统行为**：澄清必要条件 → 查询具有可信属性的商品 → 条件筛选 → 比较适配性 → 明确商品信息来源及验证状态。  
**变化注入**：遇到不明商品医疗功能宣称不得编造；遇到药品相关需求应遵循更高要求的信息边界。  
**演示价值**：约束满足、工具选择、结果引用与医疗商业分离。

### 6.6 Journey F：专业工具接入（最后阶段）

**输入**：用户希望查看一段时期的指标趋势，并据此回顾已有生活管理目标。  
**系统行为**：调用独立的时间序列与研究性分析工具；工具返回适用范围、数据充分性、模型版本与局限；Agent 整合为解释，并在需要时请求用户确认任务调整。  
**变化注入**：样本缺失或模型不适用，系统明确不计算个人风险值，不以 LLM 自行填充。  
**演示价值**：专业工具 API/MCP 接入、模型工具边界和跨能力协作。

## 7. 核心技术能力与求职价值映射

这一章规定**技术必须为什么产品行为服务**，不取代详细架构。

| 技术主题 | 必须能展示的外部行为 | 不应采用的伪证明 |
|---|---|---|
| Tool Calling | 动态选择真实工具并使用真实结果 | 只打印“已调用工具” |
| Agent Loop / ReAct | 依据 observation 决定下一动作 | 固定按五步脚本执行 |
| Planning / Replanning | 用户改目标后局部修订并继续 | 永远从头重新运行 |
| Context Engineering | 长任务保持正确约束、减少无关上下文 | 把全部历史放入 Prompt |
| Memory | 跨会话延续、处理冲突和撤销 | 仅向量化所有聊天文本 |
| MCP / Skills | 规范接入、能力发现、按需加载 | 把每个函数都包装成 MCP |
| Agentic RAG | 根据问题检索、重查、引用或说明不足 | 只调用一次向量搜索 |
| Harness | 测试规划辅助、上下文卸载、工具治理的增益 | 重写一整套 Runtime |
| Evaluation | Baseline、分层指标与可重现失败分析 | 凭演示感觉得出成功率 |
| Multi-Agent（可选） | 实验能证明隔离或委派带来收益 | 仅增加多个角色聊天 |
| Computer Use（可选） | 在受控模拟环境完成实际 UI 操作 | 通过截图宣称自动化成功 |

### 7.1 必做、研究、可选三级

**必须实现且验证**：模型调用、Agent Loop、工具使用、必要的规划、状态/记忆、基本 RAG、数据隔离、安全审批、Trace 与任务评测。  
**重点研究并形成对照实验**：Harness、上下文工程、Temporal Memory、动态 Replanning、Skills 能力选择。  
**仅在任务驱动且收益明确时增加**：Multi-Agent、浏览器 Computer Use、知识图谱、领域微调、Agent RL、大规模分布式 Runtime。

这不是降低技术深度，而是确保每个进入项目的技术都有现实问题、基线、实现与效果证据。

### 7.2 八大智能的定位

语义理解、上下文、关系连续性、情绪理解、目标与隐含需求推断、对话策略、主动性和自我约束，作为**横跨任务的行为能力模型**，不是八个独立 Agent 或八个医学模块。各能力的操作性定义、负面案例、技术承载和测试方法在 08 维护。

## 8. 范围、边界与关键权衡

### 8.1 产品内（In Scope）

- 一个主 Agent 与统一任务工作台。
- 真实可用的领域工具、知识库、合成健康数据和报告样本。
- 个人任务与记忆的授权管理。
- 健康人体导航、数据趋势与解释交互。
- 受限的健康设备/商品信息比较。
- 与健康管理有关的规则、研究性分析及事件任务。
- Harness 配置与实验、任务级评测、运行轨迹。

### 8.2 产品外（Out of Scope）

- 临床诊断、处方、实时医疗急救服务、商业化医疗建议或医疗器械合规宣称。
- 真实医院信息系统上线、真实患者数据采集、多机构身份互认。
- 公司专有知识和业务规则的直接迁移。
- 建造全功能电商支付平台。
- 从零开发基座模型、通用分布式执行平台或自研所有基础组件。
- 为显示技术数量而预设多个子 Agent、知识图谱及浏览器自动化。

### 8.3 六项设计权衡

1. **Agent-first vs Runtime-first**：优先完成模型驱动真实任务，Runtime 能力复用成熟框架。
2. **自主性 vs 确定性**：自由选择合法任务策略，医疗规则/权限/持久化副作用使用确定性校验。
3. **广度 vs 深度**：覆盖多领域协作，但每个领域只做最能测试 Agent 的代表性任务。
4. **长期记忆 vs 用户隐私**：最小化持久化，保留来源、撤销和隔离。
5. **视觉表现 vs 数据可信**：人体图是导航，不制造无依据的器官评分。
6. **前沿技术 vs 可交付性**：研究内容必须可以对照实验验证，不能阻塞核心产品里程碑。

## 9. 实现演进与最终形态的关系

本章只描述产品能力的**出现顺序**；具体开发任务与门禁在 06 定义。

| 产品演进 | 用户可见能力 | 主要技术证据 | 最晚要保持的通用性 |
|---|---|---|---|
| E1 对话底座 | 流式多轮对话 | 模型适配/基础上下文 | 不含医疗专属代码 |
| E2 通用 Agent | 工具任务、暂停/恢复、基础记忆 | Agent Loop、Tools、Trace | 完成非医学任务 |
| E3 健康知识 | 可信科普问答与引用 | RAG、检索评测 | 知识集合可替换 |
| E4 健康中心 | 人体图、指标、趋势和分析 | 数据工具、状态和可视化 | 健康域为独立能力 |
| E5 报告处理 | 上传、提取、校正、对比 | 文档工具与工作流协作 | 同类文档可扩展 |
| E6 购物辅助 | 商品搜索、条件筛选 | 多工具选择/约束 | 无真实购买依赖 |
| E7 长期管理 | 监测事件、目标、专业模型 | Long-running / Event-driven | 领域计算独立工具 |
| E8 问诊集成 | 受控调用 AIdoctor | Handoff、接口安全 | 不修改其临床主链 |

情感支持作为横向能力在 E2 形成支持性对话基线，E4/E7 逐步添加授权记忆与主动任务。Harness 和八大智能不单独构成新产品阶段，而持续伴随各阶段评测和优化。

## 10. 非功能产品要求（面向用户与展示）

以下是目标级要求，具体数值和压测条件需在 06 中固定后评测；不得在未实测时写成“已达标”。

### 10.1 可解释性

用户能理解完成了什么、用了什么数据、哪些结论有来源、哪些推断有不确定性。开发者能定位每一步工具的可公开输入/输出及结果来源。

### 10.2 可恢复性

用户刷新页面或服务异常恢复后，任务进度应可重新查询；等待审批的任务不能因为重试而越权完成。副作用重试需要幂等或明确的结果核对。

### 10.3 安全与可信

使用公开/授权/合成数据；最小权限；跨用户数据隔离；系统明确医疗信息的能力边界，不能因为无法回答就捏造指标或患者历史。

### 10.4 可复现性

技术面试官能够通过 README、环境模板、合成数据和一键脚本启动主要组件，在不需要企业内网或私人秘钥的情况下复现公开任务。模型 API 密钥允许由本地环境注入；公开项目不包含密钥。

### 10.5 可扩展性

至少完成一次新增非医学工具/能力包的测试，不改动 Agent Loop 主体即可完成登记、授权、调用、追踪与评测。

### 10.6 成本可控

评测脚本可配置模型、最大步骤、Token 限额和调用预算；提供轻量测试模式和适当缓存。外部付费 API 不是必须绑定到特定品牌。

### 11.1 演示路线（建议 15–20 分钟）

1. 非医疗任务：实时展示 Tool Calling 和工具失败后的处理。
2. 健康中心：查看合成用户数据并触发一次跨工具分析。
3. 中途更正/审批：展示数据更正、计划调整与受控写入。
4. 长期连续性：演示新会话记忆与计划状态，并指出安全边界。
5. Benchmark：展示 Baseline、改进配置及失败类别，不只展示平均分。

### 11.2 简历素材验收

最终简历中的量化结论必须有实验对应：测试集规模、模型版本、成功率定义、重复次数、成本或延迟计算方式。不能把设计目标当作已实现事实。

## 12. 关键风险与退出条件

| 风险 | 表现 | 缓解方案 | 停止扩展的信号 |
|---|---|---|---|
| 领域功能膨胀 | 不停扩展病种和商品目录 | 每阶段仅验证代表任务 | 无法稳定演示通用 Agent Loop |
| Runtime 过度设计 | 先花大量时间实现调度基础设施 | 优先使用 LangGraph / 成熟组件 | 基础执行未跑通却冻结大量契约 |
| 伪 Agent | 硬编码全部业务分支 | 加入未知措辞和变更任务 | 模型无法在合法工具中自行选择 |
| 假评测 | 只测幸福路径或让模型自评 | 确定性结果 Oracle + 负例 | 无法解释失败和重现结果 |
| 医疗越界 | 合成研究模型被解释为诊断 | 明确研究用途/验证状态 | 演示涉及自动处方/治疗决策 |
| 数据产权风险 | 使用内部文档或客户数据 | 仅独立设计与公开许可数据 | 无法说明数据来源及授权 |
| Harness 研究失焦 | 研究变为重写 Runtime | 先定义可检验实验假设 | 实验无衡量指标和基线 |
| 视觉优先 | 花大量时间做 3D 外观 | 先 2D 与真实交互 | UI 完整但无真实工具任务 |
