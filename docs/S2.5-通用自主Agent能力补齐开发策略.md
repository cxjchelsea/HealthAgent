# HealthAgent — S2.5 通用自主 Agent 能力补齐开发策略

> 版本：V2.0（用户确认的阶段指导基线）
> 阶段：S2.5 — General Autonomous Agent Enhancement
> 上游：S2 通用 Agent 可运行基线；下游：S3 健康知识与 Agentic RAG
> 开发策略：**18 项能力驱动、独立设计、渐进实施、端到端验收**
> 设计状态：**阶段策略已确认；各能力详细技术设计尚待分别完成**
> 仓库基线：main @ `ba4f76e1d324e045f9ee4d53a115b6ecf5d3ee22`（制定策略时）

## 1. 定位、目标与边界

S2.5 位于已具备 Agent Loop、工具调用、基础规划、会话、记忆、Checkpoint、MCP、Skills 和部分可靠性能力的 S2 基线之后、S3 领域知识开发之前。现有 S2 原型在复杂目标理解、自主规划、长任务、反馈驱动修正、智能记忆、恢复、可解释错误和 Trace 等方面尚有缺口。

S2.5 **不从头重构、不建设第二套 Agent Runtime、不提前领域化**。目标是让 Agent 能面对未硬编码完整执行流程的新任务，理解目标与约束、自主选择合理行动、依据真实工具 Observation 推进与修正、恢复可信状态、处理需要确认的副作用操作，并交付可验证成果。

成果要求：
- 理解显式与隐含目标、多目标、约束、歧义和中途更正；需要时澄清。
- 根据目标自主选择直接回答、调用工具、制定计划、重规划、暂停或结束，而非依赖固定任务脚本。
- 将计划、步骤、工具尝试、观察、结果材料与最终交付关联为可追溯状态。
- 有选择地利用会话与分层长期记忆，按授权提取、检索、更新、失效和删除。
- 具备一致的权限审批、可信边界、错误处理、执行预算和恢复语义。
- 能够以正式 Conversation API、真实工具、真实模型和可复现 Benchmark 证明能力。
- 后续 S3 新工具通过通用能力接口接入，避免反复修改 Agent 主循环。

### 1.1 不做事项

不提前实现临床问诊、健康知识索引、复杂多 Agent/子 Agent 平台、分布式 Scheduler、额外 Runtime、知识图谱或向量记忆基础设施。是否采用额外设施由实际数据规模和 Benchmark 收益决定。

### 1.2 开发纪律

**18 项能力是开发与验收主线**；不再以原先“五层”或“三阶段”作为强制划分。五层可用于理解旧讨论，但不决定交付排序和完成标准。

每项能力**设计可以独立，接口必须统一；实现可以渐进，验收必须端到端**。优先复用当前仓库，只有真实证据证明不满足目标时才做定向结构调整。不能为通过单个语句测试而增加硬编码工具调用序列；确定性代码用于校验、权限、持久化、幂等和安全，模型负责适合模型完成的语义理解、选择及规划。

## 3. 每项能力的统一实施闭环

### 3.1 目标与行为定义
说明要解决的用户问题、目标智能水平、正常行为、失败及边界行为、不做事项。关注 Agent 是否实现用户目标，不把“增加一个类/端点”视为交付。

### 3.2 当前代码与 Gap 审查
以**当时最新 main 精确 SHA**核对入口、调用路径、数据和测试，分别标记已实现、部分实现、未实现、证据不足。列出可复用、应改造及需新增部分。不得只凭 PR 描述或名称推定已实现。

### 3.3 独立详细设计
每项设计至少给出：
1. 用户可见行为、核心场景和验收准则；
2. 技术方案、替代方案及取舍；
3. 决策机制、执行流程和状态转换；
4. 输入/输出契约、持久化与生命周期；
5. 与其他能力的接口和统一对象边界；
6. 异常、冲突、权限、可信与恢复策略；
7. 代码影响范围、兼容性和非目标；
8. 自动化、API 集成、真实模型 E2E、对抗场景及可复现证据。

设计深度按能力复杂程度调整，不要求 18 项拆为 18 个服务或进程。

### 3.4 渐进代码实现
在现有 HealthAgent 的单一 Agent 主链中集成；保持已有 API、数据库和安全控制可回归。需要变更共享契约时进行影响分析与兼容迁移。允许一个能力包含多个 PR，也允许一个小 PR 触及必要的相邻能力；**PR 数量不是进度指标**。

### 3.5 三种证据级别
- **确定性单测**：Schema、状态转换、边界、权限、错误、幂等。
- **集成测试**：正式 API、真实测试数据库、受控工具、跨轮与恢复。
- **真实模型 E2E**：真实 Qwen 等明示模型执行未知/变体任务；保存模型配置、Prompt、工具版本、任务、结果和 Trace。
Fake Provider 结果不能冒充真实模型。必须覆盖失败场景；需要时多次运行并报告波动。

### 3.6 能力收口
记录精确 Git SHA、功能与证据、失败项、限制、兼容情况及影响的相关能力。只有达到事先明确的行为门槛方可 `CLOSED`。全局状态采用 `NOT REVIEWED / DESIGNING / READY TO IMPLEMENT / IMPLEMENTING / VERIFYING / CLOSED / BLOCKED`。

## 4. 重点能力的专项设计约束

### S25-01：模型驱动的目标理解
不使用关键词分类作为核心理解机制。优先以 LLM 结构化语义解析 Goal、Constraints、多目标、歧义、信息缺口、继续/更正/取消等变化；以 Schema、可信上下文及确定性策略检查一致性和安全性。关键词/正则可用于显式命令或安全兜底，**不能代替通用语义决策**。不默认需要训练专用意图分类器。

### S25-02：统一决策主链
保留一条 `Understand → Decide → Act → Observe → Continue / Replan / Clarify / Finish` 主链，另外明确 `Paused / Denied / Failed / Budget Exhausted / Cancelled` 路径。不能不断为固定自然语言句式添加绕开主链的执行补丁。

### S25-03 / S25-06 / S25-07 / S25-08：可信任务执行
区分 Goal、TaskState、Plan、Step、Attempt、Observation、Artifact 和 Finalization。简单任务可以直接 ReAct，复杂任务才形成显式计划；状态与依赖必须可信。失败可重试/不可重试/权限冲突要分类处理；重规划保留仍有效的完成步骤。**工具 `ok=true` 不代表目标必然完成**，最终答复需有真实证据支撑，解释未完成项。

### S25-09：上下文治理
区分当前工作上下文、历史消息、摘要、有效约束和可信任务事实。选择信息时考虑相关性、有效期、来源及预算；避免历史文本覆盖系统指令或以错误摘要污染结果。

### S25-10：智能分层记忆
单独深入设计：工作记忆、会话/短期记忆、情景记忆、语义/长期记忆；Skills/程序性知识保持独立，Checkpoint/任务事实不混入用户记忆。实现模型辅助提取、记忆价值判断、显式写入授权、重复与冲突整合、语义筛选、来源与时效、失效/删除。可先用 PostgreSQL 结构化存储结合模型筛选，不强制使用向量库或知识图谱；数据库只提供存储，智能性体现在准入、检索、整合及纠错机制。

### S25-11：恢复是恢复可信执行现场
不只恢复 `pending/completed`；要考虑工具结果引用、尝试/步骤标识、有效授权、未知执行结果、外部副作用幂等及目标更正。无法确认结果时安全暂停，不凭模型推断宣称成功。

### S25-12 / S25-13：模型提议不等于授权
区分 Action Proposal、Authorization 与 Committed Effect；高风险或持久写操作获得有效审批前不得执行。工具文本是低信任数据；参数验证、用户隔离、授权、最小权限和写操作防重为硬约束。

### S25-14 / S25-16：可恢复且用户可控
统一明确错误码、可重试性、失败原因、用户建议；用户能澄清、更改、暂停、取消、批准、拒绝及继续任务。模型不能把失败伪装为完成。

### S25-15：Harness 而非第二个 Runtime
支持上下文装配、版本化 Skill、工具暴露、任务工作空间、执行与 Token/成本预算、可切换策略。复杂特性依据同任务对照 Benchmark 的收益决定是否启用，不提前上多 Agent 或重型调度。

### S25-17 / S25-18：贯穿开发的证据链
Trace 将 Goal → Plan Revision → Decision → Action Attempt → Observation → State Transition → Termination 关联，并对敏感数据脱敏。Benchmark 依据真实业务最终状态评分，不以 HTTP 200 或模型自评取代；记录失败案例、模型版本、成本与回归。两项从首个能力工作包起持续演进。

## 5. 跨能力依赖规则

**先满足最小依赖，再深化当前能力**。Understanding 会影响 Planning/Context；Planning 需要基本 TaskState；Memory 依赖上下文、写入权限；Recovery 依赖可信执行证据；Tool Selection 依赖 Registry 与授权元数据。

开始 S25-01 前，只需核对现有共享契约并约定必要的最小对象语义，如 `GoalSpec`、`Decision`、`TaskState`、`ActionProposal`、`Observation`、`ExecutionResult`；**不提前冻结几十个未来对象**。跨能力改动必须运行相应回归，发现契约冲突先审查再调整。

## 6. 工作组织与质量纪律

- 当前主要聚焦**一项能力**，允许完成直接依赖的少量配套工作。
- 每项独立设计、代码审查、端到端集成、自动化与真实模型验证、收口记录。
- 新功能不得破坏现有 Conversation API、已持久化任务和用户隔离。
- 不硬编码具体测试话术、任务答案或工具顺序。
- 不将 CI 通过直接等同 Agent 智能水平达标。
- 不将计划中的高级能力描述为已经实现。
- 每次记录为何修改、具体差异、风险、测试结果、未完成事项；严格区分 mock、真实工具、真实模型、模拟故障与真实物理故障。
- S2.5 开发工作由能力和实际证据推动，不以架构文档数量、代码行数或 PR 数量作为完成度。

## 7. S2.5 最终验收与进入 S3

18 项能力均在约定范围内完成设计、集成与证据验证；正式 Conversation API 能运行非硬编码的新任务，具备真实工具 Observation 驱动的执行与修正；可正确处理工具异常、目标变动、记忆、权限拒绝、恢复和可信结果交付；无影响正确性、安全性或可信状态的开放阻塞项；综合 Benchmark 具有可复现真实模型配置、结果及失败分析。

完成后进行一次**跨能力综合验收**，再对照原 S2 退出要求确认是否可转向 S3。原 AC01～AC10 可在能力补齐后用于最终门禁复核，**不以它们取代 18 项能力的独立设计与实施流程**。

## 8. 正式启动前的决策与下一步

本文件是**开发策略指导文件，不是 18 项能力的全部详细实现设计**。当前不因文件落地而自动启动代码改造。

下一步：以启动时最新 main 为依据，从 **S25-01 意图、目标与约束理解** 开始，先审计 `agent/understanding.py`、`agent/loop.py`、正式 Conversation API、Context 和已有目标更正机制，再进行模型驱动结构化理解的详细设计。设计经确认后渐进实现、集成、验证、收口，然后推进下一能力。
