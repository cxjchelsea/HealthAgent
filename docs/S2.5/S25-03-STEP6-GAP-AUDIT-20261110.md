## 2. G03-01：保存计划历史结果不可完整跨轮读取（P1）

### 证据链

1. `agent/loop.py` 的受准入计划运行可调用 `calculate`、`utc_time`、`list_tasks`、`mcp_reference_lookup`、`recall_memory`，调用结果会进入 M4 `PlanReadInvoker`。
2. `agent/plan_read_invoker.py` 采用 `journal.begin -> execute_tool -> journal.record_receipt`，该链路不丢执行顺序。
3. **关键截断**：`services/plan_dispatch.py` 的 `record_receipt` 仅写：
   ```python
   bounded = {"ok": observation.get("ok") is True,
              "error": str(observation.get("error", ""))[:80]}
   if observation.get("ok") is True and "value" in observation:
       bounded["value"] = str(observation["value"])[:256]
   ```
   没有保留 `utc`、`tasks`、`source`、`definition` 和 `found`。
4. `services/s25_03_projection.py` 从已 checkpointed 的 `dispatch.receipt_json` 调用 `bounded_projection`；因为上游回执已丢字段，该函数无法恢复实际观察结果。
5. `apps/api/main.py` 的 GET `/conversations/{cid}/turns/{turn_id}/evidence` 只读持久 `AgentAttempt.result_projection`，没有合法的另一个来源可补造字段。

### 可复现实例（代码合同）

一份通过 M4 执行的 `utc_time` 原始成功观察 `{"ok":true,"utc":"2026-11-10T00:00:00Z"}`，持久回执会退化为 `{"ok":true,"error":""}`。结果投影只剩 `{"ok":true}`；历史读取不能返回 UTC 时间。这是**代码确定性的字段流失**，不是 Qwen 表达问题。

同理，M4 的成功 `list_tasks` / MCP 检索没有可跨轮复原的列表/定义。S25-03 最初核心场景 TS04、E03 要求过去已完成步骤的可信具体结果可安全交付，因此该问题应作为 S25-03 当前功能验收的 **P1 阻断项**，但不代表 S25-05 合并本身需要回滚。

### 约束下的整改方案（尚未实现）

- 由 **M4 Host 可信执行回执**产生统一有界、字段白名单的结构化 `receipt projection`；不要从模型回答、Trace 或用户字段重建。
- 保留现有 `ok/error/value` 与 `PlanToolDispatch` 的 `dispatch_unknown / observed / checkpointed` 状态机和原有 `receipt_json` 读取兼容契约；如增加版本化投影字段，必须明确定义如何兼容已有收据和离线恢复。
- `recall_memory` 不应因功能补齐而把敏感记忆原文写进永久 Evidence；只允许 `found`、`redacted` 或受控引用。`list_tasks` 如包含个人待办，应按投影大小/隐私策略返回受限元数据，不能直接落原始任务清单。
- 为 `calculate`、`utc_time`、`list_tasks`、`mcp_reference_lookup`、`recall_memory` 做同构回执字段表和失败、未知、超限负例。**S25-03 的“历史结果交付”应明确说明哪些字段可回放、哪些必须 `not_recorded/redacted`**。
- 执行前先建立回归：对当前实现检查 UTC/time 这类字段当前缺失（失败预期）；修复后验证 M4 Journal→S25-03 投影→HTTP Evidence 完整链，并回归 PostgreSQL crash/recovery，不增授权路径。

## 3. G03-02：状态历史最多返回前 100 条（P2）

`AgentTaskStateStore.history()` 按 `revision, created_at, id` **升序**排列再 `.limit(100)`，`task-history` 没有分页参数。任何超过 100 条的长期活跃任务，用户看到的都只会是最旧 100 条，无法浏览最近进展。

建议：
- 优先按 **最近优先** 做有界查询，并返回明确 `has_more`；后续根据前端需求实现 keyset cursor。
- 保持事件实际追加顺序和存储不可变，不需要将数据库历史重写为倒序。
- 测试 101+ 条数据验证最新 transition 可见，跨用户读取仍为 404，且响应有大小上限。

## 4. G03-03：M4 Tool Version 没有延伸到 S25-03 Attempt（P2）

`PlanToolDispatch` 已有可信 `tool_version`，新计划使用 `legacy-plan-v1`；但是 `project_finalized_turn` 生成 `AgentAttempt` 时没有填 `tool_version`，故列保持 NULL。此处**不应拿 Registry `1.0.0` 或当前执行器版本进行反向推断**；仅能在创建投影时复制当前可信 Dispatch 的**原值**（含 NULL），并新增旧收据兼容回归。

目前 API 的 evidence response 也未暴露版本字段；若加，需保持只读和 owner 隔离。此项影响可追溯性，不单独证明派发安全问题。

## 5. 已有正确边界，不重做

- `get_owned` 对 Conversation 检查 owner，错误返回 404；Turn Evidence 还按 conversation 检查 Turn；这是有效的代码级访问围栏，待 HTTP 双用户实测。
- S25-03 投影仅接受已 checkpointed M4 Dispatch，并强校验 step ID、工具名、参数与成功 receipt，不能用模型 Trace 直接制造成功 Attempt。
- `AgentTaskStateStore.save_in_session` 的 revision CAS 与绑定到 durable succeeded Attempt 的 transition 链保留，不应另建状态权威。
- PostgreSQL 中断/崩溃测试仍独立于 SQLite；本次没有更改它们或借“通过 CI”推出未测新路径一定正确。
