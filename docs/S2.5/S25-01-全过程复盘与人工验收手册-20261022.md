## 1. 目标和边界

S25-01 要做的是结构化、模型驱动的目标理解，包括目标、子目标、明确约束、变更分类、指代及澄清；它本身不是工具授权。正式执行路径是 Conversation API → Understanding → Execution Policy → Agent Loop → 工具验证与状态持久化。约束：不使用关键词分类替代 LLM 理解；不能把 HTTP 200 当作任务完成；不允许“不要保存”的草案隐式成为持久化用户目标。按设计实际的会话消息与 Turn 审计仍需落库。

本轮只有 PR #17，未合并 main；并行 S25-02~05 不应被本轮文件变动覆盖。

## 3. 最终架构约定

**Understanding**：结构化 `goal`、`change`、`clarification`、约束；模型提议，非执行权限。生成 Schema 与 Python 的 `missing_goal` 一致性应由共同规范保障。禁止关键词硬编码意图分流。

**Execution Policy**：独立模型决策 `respond_only` / `read_only` / `execute`。分类不是写入授权，错误策略必须失败关闭，不能自动升级 execute。

**Agent Loop / Host**：respond_only 不暴露工具；read_only 仅暴露 calculate、utc_time、list_tasks、recall_memory、mcp_reference_lookup；execute 仍需工具白名单、参数校验、必要的写入同意。状态响应 `completed` 不是事实正确性的充分证据。

**Goal Store**：新建目标与追加、修改必须由可信会话状态约束；add 不能擦除原有子目标及确认约束。respond_only/read_only 不写入 Goal Store。**注意**：会话 Message/Turn 仍持久化，因此不要将“草案不保存”为“用户消息不保存”。

### 只读数据库核验（建议测试前后各执行一次）

在另一个 PowerShell 终端，位于 `D:\HealthAgent`：

```powershell
@'
import sqlite3
db = sqlite3.connect("s25_01_manual.db")
for table in ("conversation_goal_states", "conversation_tasks", "conversation_plans", "user_memories"):
    n = db.execute(f"SELECT COUNT(*) FROM {table}").fetchone()[0]
    print(table, n)
db.close()
'@ | python -
```

这是**汇总数量**，仅能作快速哨兵；逐会话、逐字段判定需按下文 SQL 查。严格验收必须检查既有记录未被覆盖，而不只是 COUNT 未增加。数据库文件必须与实际 `DATABASE_URL` 一致。

更精确的 SQLite 检查（将真实 `<CID>` 替换进去）：
```sql
SELECT version, goal_json, pending_json FROM conversation_goal_states WHERE conversation_id = '<CID>';
SELECT id, title FROM conversation_tasks WHERE conversation_id = '<CID>' ORDER BY created_at, id;
SELECT snapshot FROM conversation_plans WHERE conversation_id = '<CID>';
SELECT owner_id, key, value FROM user_memories ORDER BY owner_id, key;
```

其中记忆查询请只针对专用测试账号使用，敏感内容不要放到日志或公开仓库。尚无记录时查询返回空行是正常的，不能因此认为数据库不存在。

## 7. 人工验收证据模板

为每个用例记录如下字段（留本地，必要时脱敏）：

```text
Case ID:
时间 / Git HEAD / 模型 / provider / conversation_id:
输入:

HTTP status / Agent status / execution_mode:
```

评估规则：语义错误、无授权写入、声称执行却无成功证据、跨轮丢约束/丢任务、stale 确认生效，一律 **FAIL**；模型无法访问或本地环境不可用记为 **BLOCKED**，不算通过；`completed` 但回答不符合预期仍为 FAIL。

## 9. 经验教训

1. **同一个校验约束应该同时在生成与验收层表达**，否则模型可合法生成 Host 必拒的数据；条件 Schema 还需验证供应商真实支持。
2. **模型输出有效 ≠ 目标语义正确 ≠ 工具执行成功 ≠ 数据正确持久化**，四个层次分别验收。
3. **诊断链路本身需要端到端回归**，避免“算出了 error detail 却丢在报告外”。
4. **执行策略不是理解属性，更不是执行许可**；Host 永远负责信任边界。
5. **用户否定约束（不要保存）、历史目标和变更冲突必须落到状态/副作用断言**，不只是提示词。
6. **停止通过反复改 Prompt 追逐固定十例评分**，应使用独立契约、匿名化真实样例、状态变更证据和明确的关门标准。
