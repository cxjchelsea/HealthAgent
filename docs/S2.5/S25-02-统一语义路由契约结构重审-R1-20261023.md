## 1. Decision and evidence

**Decision: ROUTING_CONTRACT_GAP CONFIRMED; STEP5 STRUCTURAL HOLD.**
The 14-call real-Qwen round-three run (13 PASS / 0 FAIL / 1 REVIEW) establishes behavior for those scenarios, NOT unified route ownership. The repository's own `docs/s25-02-step5-control-chain-audit-20261023.md` marks CC-02 PARTIAL, CC-03 OPEN and CC-06 OPEN. The existing physical DB check is also incomplete because repeated tests have ambiguous conversation IDs. No Step 6 or merge authorization follows from this document.

Reproduced code facts:
- `apps/api/main.py`: saved-plan `review_plan_intent` and `review_plan_revision` can occur **before** `UnderstandingService.understand`; a revision can return early.
- `UnderstandingResult` has goal/change/clarification but no explicit disjoint current-turn action route, plan-control scope, or bounded pending-reference proposal.
- `apps/api/main.py` then separately invokes `classify_pending_reply`, `review_pending_reference_lookup`, `review_unsupported_capability`, `review_read_only_clarification`, `decide_execution_policy_detail`, `reconcile_execution_policy`, plan admission/authorization/scope reviews. Not all fire every turn. These classifications can duplicate or contradict semantic ownership.
- `PlanAdmission` and `ClarificationRoute` combine local proposals but do not define a single top-level source of semantic routing.
- Formal API constructs `UnderstandingService` with default `semantic_review=False`. Turning it on alone cannot repair pre-understanding plan routing.
- `agent/loop.py` already enforces scoped tool exposure and Host-supplied plan control. `PlanLedger` retains verified binding/evidence. These are assets to preserve, not replace.

**Root cause:** absence of a unified versioned, typed *turn-level semantic proposal* and one ordered deterministic *Host admission* contract. This is a structural contract gap; the observed incidents are manifestations, although individual tooling bugs can still occur independently.

## 2. Ownership: what belongs where

### S25-01 (untrusted proposal; no effects)
- Current-user goal/change, relationship to active goal or pending clarification.
- One primary turn route: `respond | clarify | agent_loop | plan_create | plan_execute_first | plan_resume | plan_revise | cancel`.
- Referent proposal (goal / saved plan / numbered step / pending slot) and user-expressed scope; explicit positive and negative constraints.
- Proposed input-value spans/field references, not fabricated tool parameters.
- Ambiguity/confidence/reason; `clarify` when unresolved. An uncertain route must not fall through to a different effectful route.
- Suggested read-only vs mutating action category can be present as **intent**, never authority.

### S25-02 + Host (trusted admission and lifecycle)
- Authoritative session owner, concurrency, replay and request-id idempotency.
- Checkpoint/GoalStore/Turn versions, valid plan/step referents and permissible state transitions.
- Tool registry, schema, actual argument extraction/provenance from **current user request** or bound pending original request, side-effect permission and consent.
- `respond_only` cannot become a write authorization. An explicit independent tool request cannot silently execute a saved plan.
- Running plan steps, real Observations, retries/termination and evidence-based completion.
- Atomic local durable commit; external side effects require separately documented recovery boundaries, not an assertion of exactly-once.

### Permitted pre-semantic Host gates
Ownership/auth, duplicate request, running turn, explicitly typed goal_confirmation with version, malformed checkpoint, stored pending action read, and narrowly objective source conflicts may execute before S25-01. They may **reject or require clarification**, never select an alternative semantic route.

## 3. Proposed R1 contract (design sketch, not code)

`TurnSemanticProposalV2`:
- `schema_version: "s25-route-v2"`
- `goal: GoalSpec | null`, `goal_change: GoalChangeProposal | null`
- `primary_route`: one of the eight mutually exclusive route labels above
- `route_target`: `none | active_goal | saved_plan | pending_clarification | tool_action`
- `reference`: optional typed proposal `{kind, step_number?, pending_field?, candidate_span?}`
- `execution_scope`: `none | first_step | remaining_steps | all_steps | single_tool`; only valid for corresponding routes
- `effect_intent`: `none | read_only | mutation_requested`; semantic signal only
- `explicit_constraints`: structured evidence for no-save/no-execute-old-plan/no-write and quantitative limits
- `clarification`: `{required, reason, question?}`
- `ambiguity`: `{state: clear | needs_disambiguation | unreliable, reason_code}`
- `source_evidence`: bounded spans of the **current user's message** (never instructions from previous model output)
All combinations must be cross-field validated; invalid / inconsistent output does not auto-repair into an effectful route.

The model does **not** output `authorized=true`, `tool_exists=true`, `verified=true`, or `step_completed=true`. No speculative PlanLedger content is trusted as an existing checkpoint.

### Host admission results
`AdmittedTurnRoute` = `respond | clarify | ordinary_loop | create_pending_plan | revise_pending_plan | execute_saved_first | execute_saved_remaining | cancel_no_side_effect | reject`, plus explicit `denial_reason`, `authorized_tool_scope`, `validated_binding`, and `checkpoint_revision` as Host-owned values.

This separation means one semantic *proposal* can coexist with multiple **deterministic safety checks**; it does not mean literally one model call in every exceptional case.

## 4. Precedence, failure and conflict rules

1. **Host preconditions:** ownership, duplicate/running turn, explicit versioned confirmation, checkpoint structural validity.
2. **One primary semantic proposal** for the current utterance and bounded trusted context; no autonomous plan/revision classifier before this step.
3. **Validation:** reject unsupported route/field combinations and mismatched source spans. If unreliable or competing referents, return a clarification; never reinterpret as permission.
4. **Host admission:** bind trusted saved plan and revision, pending action owner/original source, registered tools and schema. Keep plan creation separate from plan execution. Reject completed-step replays; selected first step must never silently become the next unfinished step.
5. **Permissions:** start from the least permissive interpretation consistent with the explicit current request. A secondary semantic review may clarify scope or narrow permissions; any proposed escalation requires **new explicit user authorization**, not just a second model opinion.
6. **Execution:** route to existing AgentLoop (normal) or bounded saved-plan executor (plan). A read-only standalone tool action never receives saved-plan control.
7. **Observation and durable outcome:** only observed matching tool evidence changes step status; final response must not attach irrelevant plan-pending warnings to an independent standalone result.

Trust boundary note: a reference to a previous plan/pending slot can be resolved from stored Host state, but arbitrary tool parameters introduced by a model are not source-authorized. Pending clarification only fills the one originally bound field. Ambiguous edits do not mutate state.

## 5. Required cross-route matrix (minimum)

| Existing state | Current user intent | Proposal | Required Host behavior |
|---|---|---|---|
| none | text draft, do not save | respond | no PlanStore/TaskStore writes |
| none | explicit task creation | agent_loop + mutation_requested | permitted named task only, no plan |
| none | lookup with missing term | clarify | save narrowly typed pending field, no tool |
| pending lookup | reply "RAG" | agent_loop / clarification resolution | fill only original lookup.term; no new tool |
| saved pending 2-step plan | independent calculate; do not execute saved plan | agent_loop | calculate; snapshot unchanged |
| saved pending 2-step plan | change step 2 from 8*8 to 9*9, not execute | plan_revise | validated binding, new revision, no tool |
| saved pending 2-step plan | execute only first | plan_execute_first | precisely step 1 only |
| first completed | execute first again | plan_execute_first | status/rejection, not step 2 |
| first completed | continue all remaining | plan_resume | only pending authorized bindings |
| all complete | repeat resume | plan_resume | no tool calls |
| no saved plan | resume existing | plan_resume | ask/create-plan guidance; no invented checkpoint |
| any | named unregistered shell | agent_loop / clarify/reject | no unregistered execution; honest refusal |
| any | ambiguous tool or step referent | clarify | no writes, no tool call |
| pending task title | unrelated new chat | respond/agent_loop | must not create task |
| user requests confirmed-constraint correction | goal-change proposal | Host versioned confirmation | no implicit mutation |

Add variants: Chinese/English paraphrase, negative constraints, missing values, model schema violations/timeouts, stale plan revisions, duplicate request IDs, concurrent requests, wrong owner, prompt injection inside retrieved text.

## 6. Migration scope and sequencing (NO implementation yet)

**M0 — freeze observed behavior and failure corpus.**
Pin PR #22 HEAD, the three real-Qwen reports, CI and selected DB evidence. Record original outputs and current safety invariants. Do not rewrite old observations as passing a newer schema.

**M1 — contract agreement.**
Approve route vocabulary, validation precedence, Host authority table, ambiguous-response semantics, and compatibility between `UnderstandingResult v1` and `TurnSemanticProposalV2`. Decide whether v2 is a versioned extension of S25-01's model or a single adapter over its goal proposal. Both must still yield one authoritative semantic proposal per turn.

**M2 — shadow-only evaluation.**
Compute v2 in parallel for recorded/synthetic cases, but do NOT use it to control tools or persistence. Compare v1+existing route vs v2. Log only redacted route diagnostics and number of semantic model calls. Fail on unexplainable differences.

**M3 — Host single admission cutover.**
Only after matched tests: replace the separate semantic dispatch paths with one admission result. Preserve every existing Host invariant, checkpoint, idempotency and non-escalation rule; do not delete independent safety guards merely to reduce model-call count.

**M4 — real execution gate.**
Run full CI and all D03/D05/D06/E03/E04/E06/F02/F03/F04 cross-route suites, plus multi-paraphrase real Qwen including adversarial boundary cases. Verify actual Store/Turn readback with exact per-run conversation IDs and request IDs; resolve the previous duplicate-conversation ambiguity. Check no safety regressions, no fabricated tool evidence, no unauthorized writes.

**M5 — retirement / closure.**
Remove only redundant semantic classifiers after equivalence evidence; keep compatibility adapters if old API consumers still exist. Explicitly document remaining F04 structured refusal inconsistency, E06 irrelevant plan-status suffix, external side-effect crash window and scope of acceptance.

These M0–M5 are design review checkpoints within **S25-02 Step 5**, not new S2.5 feature numbers or a replacement for the project's six-step governance.
