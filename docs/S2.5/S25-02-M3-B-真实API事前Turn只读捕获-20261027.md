## Scope implemented

The existing `/conversations/{cid}/agent/messages` endpoint captures a bounded `CapturedTurn` snapshot inside the same `Session.begin()` transaction that inserts and flushes the Turn, after reading the conversation's `ConversationPlan` row and before committing the Turn-creation transaction. This is before the legacy goal/plan/tool path. The snapshot binds `conversation_id`, `client_request_id`, and the new `turn_id`, plus checkpoint presence/revision and pending-presence/provenance booleans. It computes a canonical SHA-256 digest of the checkpoint in memory; the digest and checkpoint content are not returned by the API.

At the beginning of the legacy execution path, the endpoint independently loads `existing_checkpoint` through `ConversationPlanStore.load()`. If the M2 shadow diagnostics run, the response now includes:

- `route_shadow.m3_preturn_identity`: `MATCH` / `MISMATCH` for exact Turn identifiers; `authorization_verified` is always false.
- `route_shadow.m3_checkpoint_snapshot`: `SAME`, `CHANGED`, or `UNVERIFIABLE` when comparing the captured checkpoint digest with the separately loaded checkpoint supplied to the legacy route path.

The comparison catches observable checkpoint drift between these two reads, including a changed payload that improperly retains the same revision. The SQLite integration test exercises capture in one transaction, a durable checkpoint update in another, and detection from the later read. Key ordering does not create a false mismatch.

Capture is conditioned on `settings.route_shadow_enabled`. The existing legacy execution and transaction finalization are unchanged. The new diagnostics are never passed into `decide_admission`, `execute_tool`, plan CAS, or a dispatcher. The endpoint's default behavior remains unchanged when shadow diagnostics are disabled.

## Important unresolved trust gap

This is **drift detection, not concurrency control**. The Turn-creation transaction does not guarantee that SQLite and PostgreSQL provide identical snapshot isolation semantics. The checkpoint is read again before legacy routing, but there is no demonstrated lock/CAS boundary that prevents a concurrent plan update after that second read and before dispatch. A `SAME` result only says the two observed checkpoint payloads match; it is not proof of authorization, idempotency, session-lock ownership, durable effect readback, or route/effect parity.

The pending provenance remains bounded booleans derived from the existing latest-turn lookup; it is not a new canonical pending-state record. The existing `evals/s25_02_m3_api_audit.py` remains an audit-only checker and the overall `m3_b_gate` remains `HOLD`. Existing parity comparators do not yet establish canonical DB evidence or effect equivalence.
