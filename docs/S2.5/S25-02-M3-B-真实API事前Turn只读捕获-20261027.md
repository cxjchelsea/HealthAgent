## Scope implemented

The existing `/conversations/{cid}/agent/messages` endpoint captures a bounded `CapturedTurn` snapshot inside the same `Session.begin()` transaction that inserts and flushes the Turn, after reading the conversation's `ConversationPlan` row and before committing the Turn-creation transaction. This is before the legacy goal/plan/tool path. The checkpoint row and Turn insertion are therefore read/written within one transaction, although transaction isolation semantics differ between SQLite and PostgreSQL. It binds the pre-execution metadata to `conversation_id`, `client_request_id`, and the newly-created `turn_id`, plus only checkpoint-presence/revision and pending-presence/provenance booleans.

Capture is conditioned on `settings.route_shadow_enabled`. The existing legacy execution and transaction finalization are unchanged. If M2 shadow diagnostics actually run, a `route_shadow.m3_preturn_identity` diagnostic appears with `MATCH` or `MISMATCH`; it always includes `authorization_verified: false`. No user message, checkpoint content, tool arguments, credentials, or additional persistent writes are included in that diagnostic.

The endpoint's documented return shape and default behavior are unchanged when the shadow feature is disabled. The new diagnostic is **never** passed into `decide_admission`, `execute_tool`, plan CAS, or a dispatcher.

## Important unresolved trust gap

The checkpoint is loaded **after** the original transaction that creates the Turn, not under a demonstrated single lock/transaction encompassing the snapshot and pre-dispatch admission. Therefore this provides temporal pre-execution capture and exact identifiers, **not** an authenticated atomic Host snapshot. Concurrent mutation, replay, stale plan revision, or pending provenance may still invalidate the snapshot. A `MATCH` is identity agreement, not authorization or route/effect parity.

The existing `evals/s25_02_m3_api_audit.py` is likewise a metadata report checker and remains `m3_b_gate=HOLD`. Existing parity comparators use caller-supplied identity and observed labels; they do not prove canonical DB evidence or effect equivalence.
