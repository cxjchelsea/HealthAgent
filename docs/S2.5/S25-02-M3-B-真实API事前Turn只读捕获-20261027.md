## Scope implemented

The existing `/conversations/{cid}/agent/messages` endpoint captures a bounded `CapturedTurn` snapshot inside the same `Session.begin()` transaction that inserts and flushes the Turn, after reading the conversation's `ConversationPlan` row and before committing the Turn-creation transaction. This is before the legacy goal/plan/tool path. The snapshot binds `conversation_id`, `client_request_id`, and the new `turn_id`, plus checkpoint presence/revision and the exact pending action, clarification message ID, and a SHA-256 digest of the clarification question. It computes a canonical SHA-256 digest of the checkpoint in memory. Raw checkpoint/question text and digests are not returned by the API; pending action/clarification identity is held only in the in-process capture object.

At the beginning of the legacy execution path, existing_checkpoint is now parsed from the exact serialized preturn_plan_raw captured in the Turn-creation transaction; the route no longer performs a second independent plan read. If the M2 shadow diagnostics run, the response now includes:

- `route_shadow.m3_preturn_identity`: `MATCH` / `MISMATCH` for exact Turn identifiers; `authorization_verified` is always false.
- `route_shadow.m3_checkpoint_snapshot`: `SAME`, `CHANGED`, or `UNVERIFIABLE` when comparing the captured checkpoint digest with the separately loaded checkpoint supplied to the legacy route path.

The comparison catches observable checkpoint drift between these two reads, including a changed payload that improperly retains the same revision. The SQLite integration test exercises capture in one transaction, a durable checkpoint update in another, and detection from the later read. Key ordering does not create a false mismatch. A new `compare_pending_provenance` helper compares the exact action, clarification message ID, and question digest, returns `MISMATCH` for cross-message replay or changed question text, and never treats a missing source as a match.

Capture is conditioned on `settings.route_shadow_enabled`. The captured identity/checkpoint is still diagnostic-only and does not authorize tools. Capture of the raw snapshot now occurs even when shadow diagnostics are disabled, because it also binds the request's initial plan read to its Turn. Shadow response fields remain opt-in.

## Turn-bound CAS for no-effect plan outcomes

The API now retains the exact serialized plan snapshot (preturn_plan_raw) read inside the Turn-creation transaction and derives existing_checkpoint from that same value. The following no-tool outcomes persist the plan checkpoint with compare_and_swap_in_session() against that exact raw snapshot:

- plan_created_pending_execution
- plan_revised_pending_execution
- plan_already_completed
- plan_first_step_already_completed

If the expected snapshot is stale, the API does not overwrite the plan. It returns a bounded plan_snapshot_conflict partial result and finalizes the Turn, rather than leaving the Turn stuck in running. New static wiring tests guard the snapshot binding, the allowlisted CAS outcomes, and the conflict response.

This is deliberately not yet applied to tool-execution checkpoints. Those currently retain the legacy unconditional persistence path because the tool effect may already have happened before finalization. Applying CAS only at that point could leave a real external effect without its corresponding durable checkpoint. A pre-dispatch execution reservation/lease (or equivalent Host-owned gate) must be designed and tested before that path is switched. The CAS storage primitive itself remains useful but is not a complete execution guard.

PlanSnapshotConflict is currently handled only for the allowlisted no-effect outcomes. Other unexpected finalization errors retain the existing error handling. CI must pass before this increment is treated as validated.

## Important unresolved trust gap

This is **drift detection, not concurrency control**. The Turn-creation transaction does not guarantee that SQLite and PostgreSQL provide identical snapshot isolation semantics. The checkpoint is read again before legacy routing, but there is no demonstrated lock/CAS boundary that prevents a concurrent plan update after that second read and before dispatch. A `SAME` result only says the two observed checkpoint payloads match; it is not proof of authorization, idempotency, session-lock ownership, durable effect readback, or route/effect parity.

The pending provenance remains bounded booleans derived from the existing latest-turn lookup; it is not a new canonical pending-state record. The existing `evals/s25_02_m3_api_audit.py` remains an audit-only checker and the overall `m3_b_gate` remains `HOLD`. Existing parity comparators do not yet establish canonical DB evidence or effect equivalence.

## Next required work before M3-B acceptance

1. Design and implement a Host-owned execution reservation/lease or equivalent gate that checks the captured checkpoint and binds admission plus tool dispatch to one revision. Only after that gate is acquired should tool-execution checkpoint persistence move from unconditional save to CAS; CAS at finalization alone cannot undo an external tool effect.
2. The capture object now retains exact pending clarification provenance rather than booleans alone, with unit coverage for cross-message replay and changed question text. Still required: independently re-read canonical durable pending state at the execution boundary and prove the compared source is the one actually consumed by the route.
3. Capture the final legacy route, exact target/scope/effect and durable readback from the same Turn; compare independent observations rather than model-declared or synthetic labels.
4. Add race/replay tests that demonstrate a stale revision cannot pass the future Host gate, then run opt-in real-Qwen/API validation and inspect the evidence report.
5. Keep M3-A nonauthoritative and M3-C disabled until a separate review and explicit permission.

This document records a checkpoint-drift diagnostic increment and one SQLite integration test, **not** M3-B physical acceptance or production gate approval.
