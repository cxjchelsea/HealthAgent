# S25-02 D06 — 计划执行与故障恢复：架构整改和验收边界（2026-10-23）

## 真实问题与反补丁审查

Qwen 人工测试首先出现 `plan_not_found`（创建与执行未使用同一有检查点的会话）；在同一会话重测后计划创建成功、MCP 步骤完成，却停在第 1 步。代码审查确认两项独立缺陷：

1. `review_plan_intent` 单次返回 `execute_first/resume`，该分类直接决定执行范围，模型可能把“执行所有剩余步骤”误判为“只执行第一步”。
2. 计划恢复走 `AgentLoop.run` 内独立的 `for step in outstanding` 执行路径，`if not result['ok']: break`，没有接入普通 AgentLoop 的 C02 故障恢复能力，且缺少计划步骤绑定的可信恢复证据。

之前 D03/D05 修复过度依靠逐条模型分类、特殊文案和分支前置，本轮不继续给 D06 增加单测试文本特殊判断。

## 设计边界

- `agent/plan_execution_scope.py`：独立、Schema 约束的执行范围复核。仅允许明确的 `one`（单步）或 `all`（所有剩余步骤），不明确时保守执行一步，不让模型仅因计划存在就拥有整份计划的执行许可。已接入正式结构化 API 的计划恢复路由；在通常生产模型接线下启用，测试注入策略保留原约束。
- `agent/plan_recovery.py`：恢复策略只产出候选动作，不代表成功。实现了**通用受界限整数幂表达式**向等价乘法的转换：限制 AST 结构、整数基数大小、幂次、表达式长度，不执行 Python 任意代码。仅当原工具返回 `unsupported_expression` 时尝试；除零、工具超时、无关错误等不凭模型猜测直接恢复。
- `PlanLedger.apply_verified_recovery`：以绑定的原步骤、工具名、原参数及真正成功的替代工具 Observation 为前提，再调用 C02 的 `arithmetic_equivalent` 数值校验。验证通过才升级 revision、写 `plan_step_recovered` 事件并完成该步骤；失败时计划继续 pending，绝不因为模型 final 内容伪造完成。相邻已完成步骤不能重复执行。
- `AgentLoop` 计划执行路径调用上面的候选策略和验证，保留失败与恢复两个真实 Observation 的审计信息，不在未验证时重写检查点；用户只授权单步时不执行后续步骤。

## 非目标和后续范围

这不是通用多领域重规划器：当前自动修复器仅支持可证明等价的有限整数算术幂变换，不自动改动 MCP 查询、任务写入、数据库或其他工具目标；这些需要 S25-03/04/05 的统一步骤授权、证据与工具治理模型。范围分类与续接授权仍依赖模型，可能存在真实 Qwen 误判，必须单独做真实模型 E2E 评测。长期应该把当前 API 中多次独立的 Plan Intent/Revision/Scope 模型调用整合为一个规范化的计划控制决策接口，避免不可审计的相互覆盖。

## 自动化回归

`tests/test_s25_02_d06_recovery.py` 覆盖：
- 一次授权执行多步，第二步工具首次失败，再通过等价乘法恢复，记录版本和证据；
- 只授权第一步时后续 pending；
- 除零错误不伪造恢复、不运行后续；
- 超出允许转换范围的错误保持 pending；
- 新一轮恢复只执行尚未完成步骤，不重复第一步。
