## 1. 运行故障：本地 Ollama HTTP 502

这一节发生在正式人工验收之前。当时结构化输出失败的具体原因还没有查清，后文第 2 节的时间线把它确定为 `missing_goal`。

### 1.1 复现

Windows Docker Desktop 容器中的 Ollama 已安装 qwen3:4b 与 qwen3:14b，GPU 可识别。PowerShell `Invoke-RestMethod` 请求 `/api/chat` 成功。Python `httpx.post` 使用默认参数访问同一地址得到 HTTP 502（空响应）。改成 `httpx.Client(trust_env=False)` 后为 HTTP 200。

同一环境第一轮 Direct E2E 5/5 HTTP 503，Structured 5/5 失败。排除代理干扰后 Direct 5/5 HTTP 200，Structured 4/5 HTTP 503。代理与结构化输出是两个独立问题，不能归因于模型尺寸或 GPU。

### 1.2 根因

`httpx` 默认 `trust_env=True`，读取系统 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` / `NO_PROXY`。Windows 用户环境下代理绕路会把 loopback 本地请求送往代理，得到 502。`trust_env=False` 成功复现并隔离了这一影响，属于已验证的代理环境问题。

### 1.3 修复

- 为原生 Ollama loopback（`localhost` / `127.0.0.1` / `::1`）请求禁用 httpx 环境代理继承（`trust_env=False`），涵盖流式生成、工具决策、Understanding。非本地服务与 OpenAI-compatible 远程服务仍使用系统代理。
- 统一由 `agent/http_policy.py` 作决策。不要求在 PowerShell 里手动设置 `NO_PROXY`，也不全局清空系统代理。
- 原生 Ollama 的 `MODEL_BASE_URL` 使用 `http://127.0.0.1:11434/api`，适配器追加 `/chat`。
- Structured 增补机器可读 JSON Schema、分层错误分类与有限重试：4B 最多尝试一次，14B 遇 Schema 或一致性错误时最多重试一次。伪造 goal ID 或传输异常不在同模型上重试。失败尝试只记录错误类别与耗时，不记录原始用户文本或模型输出。保持无关键词 fallback，不绕过用户确认和目标授权。

确定性单元测试覆盖代理选择和 Structured 校验。远程 Ollama 若走代理，仍保留系统代理；本地绕行只针对 loopback。默认策略不因这次故障修复而切换。

## 2. 过程整改与人工用例

### 2.1 目标和边界

S25-01 要做的是结构化、模型驱动的目标理解，包括目标、子目标、明确约束、变更分类、指代及澄清。它本身不是工具授权。正式执行路径是 Conversation API → Understanding → Execution Policy → Agent Loop → 工具验证与状态持久化。不使用关键词分类替代 LLM 理解。不能把 HTTP 200 当作任务完成。不允许「不要保存」的草案隐式成为持久化用户目标。会话消息与 Turn 审计仍需落库。

### 2.3 当时形成的架构约定

**Understanding**：结构化 `goal`、`change`、`clarification`、约束；模型提议，非执行权限。生成 Schema 与 Python 的 `missing_goal` 一致性应由共同规范保障。禁止关键词硬编码意图分流。

**Execution Policy**：独立模型决策 `respond_only` / `read_only` / `execute`。分类不是写入授权。错误策略必须失败关闭，不能自动升级为 execute。

**Agent Loop / Host**：respond_only 不暴露工具；read_only 仅暴露 calculate、utc_time、list_tasks、recall_memory、mcp_reference_lookup；execute 仍需工具白名单、参数校验、必要的写入同意。状态响应 `completed` 不是事实正确性的充分证据。

**Goal Store**：新建目标与追加、修改必须由可信会话状态约束；add 不能擦除原有子目标及确认约束。respond_only/read_only 不写入 Goal Store。会话 Message/Turn 仍持久化，因此「草案不保存」不等于「用户消息不保存」。

为每个用例记录如下字段（留本地，必要时脱敏）：


评估规则：语义错误、无授权写入、声称执行却无成功证据、跨轮丢约束或丢任务、stale 确认生效，一律 FAIL。模型无法访问或本地环境不可用记为 BLOCKED，不算通过。`completed` 但回答不符合预期仍为 FAIL。

### 2.8 经验教训

1. 同一个校验约束应该同时在生成与验收层表达，否则模型可合法生成 Host 必拒的数据。条件 Schema 还需验证供应商真实支持。
2. 模型输出有效、目标语义正确、工具执行成功、数据正确持久化，是四个层次，分别验收。
3. 诊断链路本身需要端到端回归，避免算出了 error detail 却丢在报告外。
4. 执行策略不是理解属性，更不是执行许可。Host 负责信任边界。
5. 用户否定约束（不要保存）、历史目标和变更冲突必须落到状态与副作用断言，不只是提示词。
6. 停止通过反复改 Prompt 追逐固定十例评分。使用独立契约、匿名化真实样例、状态变更证据和明确的关门标准。

## 3. 验收结果与当轮修复

记录依据是用户在 Windows Ollama 环境提供的 `s25_01_live(5).json`、`s25_01_e2e(2).json`、PR #17 仓库代码及 GitHub CI。未在 GitHub runner 上复现本地 Qwen。PR 保持 Draft，Direct 保持默认。本文不构成合并或生产默认切换许可。

### 3.1 自动化矩阵里已经看到的

1. 理解结构与启发式语义：4B→14B 10/10，14B 10/10；两种策略均 10/10 valid。这不是复杂语义完整性认证。
2. E2E：Direct 5/5 `completed`，Structured 5/5 `completed`。各组是顺序小样本，HTTP 200 不代表回答正确。
3. Structured 模式：simple `respond_only` 无工具；task `read_only` 且 `calculate` 执行成功；plan `respond_only` 无工具；multiturn 两轮 `respond_only` 无工具。之前 plan 不必要调用 `propose_plan` 的问题在该矩阵中消失。
4. Host 权限测试：respond_only 无工具、read_only 无写工具。数据库断言验证这两种模式不写入 Goal Store。会话 Message/Turn 仍会记录，不能称为零数据库写入。
5. 生成 JSON Schema 与 Python 的 `missing_goal` 验收条件已有 `if/then` 约束，并保留严格校验。尚不能证明 Ollama 的约束生成器完全遵循条件 Schema。

同一批报告还留下这些边界：

- `missing_goal` 并非零发生：14B 的 `revise`、`add` 首轮仍可能失败并通过重试恢复。`if/then` 在实际解码器中的约束有效性仍未确证。
- `multiturn` 的第二轮「请修改第二项，其余保留」在 Structured 中以 `respond_only` 直接生成最终文字。该报告没有保存回答文本，因此不能证明第二项确实修改、其他条目完全保留。人工用例 M04 后来用截图补了这一检查。
- `add` 的 Goal Store 完整候选前缀保留规则已有单元测试。真实模型报告只证明 kind 通过，不证明多轮持久化合并正确。
- `s25_01_e2e` 对回复内容和数据库写入没有真实 provider 的断言，JSON 里也没有该证据。
- Direct 基线 `multiturn` 第二轮有四次失败的 `propose_plan`，最终仍 `completed`。这是独立的 Direct Agent Loop 质量缺口，不能计入 Structured 功能已完全收口。
- 10 个样本不足以得出稳定的 P95。单独 14B 的 P50=2738ms、P95=3407ms；4B→14B 的 P50=4043ms、P95=16063ms。本阶段保留候选配置，不立即切换默认。

### 3.2 收口前补上的 Goal Store 保护

- API 主链在 `execution_mode` 为 `respond_only` 或 `read_only` 时禁止 Goal Store 提议入库，避免「不要保存草案」在无工具调用时仍写入目标状态。
- Conversation API 的确定性回归增加数据库读回验证。execute 模式仍走原来的授权、约束确认和持久化逻辑。
- 这里的无保存只涵盖模型目标提议与写工具，不包括必要的会话审计记录。
