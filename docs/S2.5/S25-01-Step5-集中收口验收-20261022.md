## 通过的证据

3. Structured 模式：simple `respond_only` 无工具；task `read_only` 且 `calculate` 执行成功；plan `respond_only` 无工具；multiturn 两轮 `respond_only` 无工具；之前 `plan` 不必要调用 `propose_plan` 的问题在该矩阵中消失。

5. 生成 JSON Schema 与 Python 的 `missing_goal` 验收条件已有 `if/then` 约束，并保留严格校验。尚不能证明 Ollama 的约束生成器完全遵循条件 Schema。

## 未完全通过的项目和边界

- `missing_goal` 并非零发生：14B 的 `revise`、`add` 首轮仍可能失败并通过重试恢复；说明 `if/then` 在实际解码器中的约束有效性仍未确证。
- `multiturn` 的第二轮请求“请修改第二项，其余保留”在 Structured 中 `respond_only` 直接生成最终文字；该报告没有保存其回答文本，因此不能证明第二项确实修改、其他条目完全保留。
- `add` 的 Goal Store 完整候选前缀保留规则已经在单元测试覆盖，但真实模型报告仅证明 kind 通过，不证明多轮持久化合并正确。
- `s25_01_e2e` 对回复内容和数据库写入没有真实 provider 的断言；现有 JSON 也未包含该证据。后续必须在本地人工检查回答文本和观察无目标/任务侧效应。
- Direct 基线 `multiturn` 第二轮有四次失败的 `propose_plan`，最终仍 `completed`；这是独立的 Direct Agent Loop 质量缺口，不能计入 Structured 功能已完全收口。
- 10 样本不足以得出稳定的 P95 结论。单独 14B P50=2738ms, P95=3407ms；4B→14B P50=4043ms, P95=16063ms。本阶段保留候选配置，不立即切换默认。

## 本轮实际整改

- API 主链的 `execution_mode in {'respond_only','read_only'}` 现在禁止 Goal Store 提议入库，避免“不要保存草案”在无工具调用时仍隐式写入目标状态。
- Conversation API 的确定性回归增加数据库读回验证。对于 execute 模式依旧走原来的授权、约束确认和持久化逻辑。
- 明确这里的无保存仅涵盖模型目标提议与写工具，不包括必要的会话审计记录。
