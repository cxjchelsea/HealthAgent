# S25-01 根因复审与执行闭环整改（2026-10-22）

## 依据与确定结论
第五次之后真实报告：两种 Understanding 策略的 schema valid 10/10，语义 8/10；Direct E2E 5/5 completed，Structured 4/5 completed + plan partial。plan 的脱敏轨迹显示连续四次 `propose_plan` 返回 `ok=false`，没有建成任何计划（0/0），随后触发 `repeat_tool_stop`。因此本次不是 Ollama、代理、显存或 JSON Schema 问题；是「用户要求生成文字草案」与「Host 创建运行时执行计划」没有明确的能力边界，导致工具误用和失败后缺乏有效恢复。

原评测另外发现 add 被理解为 revise；clarification 的 `query_status + clarification_required + missing_referent` 被机械枚举评分误拒。语义评测不能将 JSON 合规直接等同于语义正确，也不能把非关键 kind 与明确澄清能力混为一谈。

## 本轮架构性修复
1. 增加理解结果 `execution_intent`（respond_only/read_only/execute，默认 execute 兼容历史），由模型理解形成提议。该字段只能缩小调用能力，不可授予新的权限。`respond_only` 在 Agent Loop Host 中移除所有工具：无论模型如何要求工具都不得执行。这将写文字草案与持久化 PlanLedger 明确隔离。原始文本和下游提示词并不具备执行权限。
2. 修订 add/revise 的定义：add 保留已完成目标并增加新内容；revise 替换、删除或修改原内容。仅靠提示词无法形式证明每次语义正确，必须依赖实测和基于状态的约束核验。
3. 工具失败轨迹增加 `error_code`（不记录参数和隐私文本），连续两次失败的计划工具请求允许一次纠正，然后停为 partial，不能伪造完成、不得污染确认目标。
4. 评测澄清场景按一致的澄清状态、原因、问题判定，不把单个可争议的 `kind` 标签当作唯一正确答案。

## 仍需证明
CI 仅证明确定性回归，不能证明模型会将所有不保存草案分为 respond_only。真实 E2E 新报告必须检查 `plan` 为 completed、0 次 `propose_plan`，以及 add 对已有三项的保留且不会篡改确认约束；对局部读工具需要进一步验证只读权限围栏。不能宣称彻底消灭随机模型错误，需以失败关闭、可观测性、行为门禁保障系统行为稳定。PR #17 保持 Draft，不能提前切换 Structured 默认策略。
