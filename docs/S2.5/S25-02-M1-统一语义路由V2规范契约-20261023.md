## 0. M1 decisions and out-of-scope

**Single current-turn semantic proposal, independent Host admission, unchanged execution authority.** A single proposal means there is ONE primary intent owner; it does not ban a narrowly scoped clarification/reliability review. Multiple sequential reviewers independently changing the user's action are not an acceptable implementation.

M1 is *contract design only*. No code or tool behavior is changed, no migrations, no shadow traffic, no real Qwen retest, no Step 5 sign-off. The plan editing interface's existing single pending calculate-binding capability remains the initial executable scope; a semantic proposal naming another kind of edit does not expand it. No rewrite of AgentLoop, PlanLedger, Tool Schema or stores.

## 1. Typed schema (normative draft)

```python
class SourceSpan:
    start: int              # zero-based Python Unicode code point offset
    end: int                # exclusive, 0 < end-start <= 400
    exact_text: str         # MUST equal current_message[start:end]

class ReferenceProposal:
    kind: Literal["none","active_goal","saved_plan","saved_step","pending_slot"]
    step_number: int | None           # 1..8 only when saved_step
    pending_field: str | None         # existing trusted pending field, if applicable
    mention: SourceSpan | None        # explicit evidence if user supplied it

class Ambiguity:
    state: Literal["clear","needs_disambiguation","unreliable"]
    reason_code: Literal["none","missing_referent","missing_argument",
        "conflicting_constraints","ambiguous_scope","uncertain_intent",
        "schema_inconsistency","model_unavailable"]

class TurnSemanticProposalV2:
    schema_version: Literal["s25-route-v2"]
    goal: GoalSpec | None
    goal_change: GoalChangeProposal | None
    primary_route: Literal["respond","clarify","agent_loop","plan_create",
        "plan_execute_first","plan_resume","plan_revise","cancel"]
    route_target: Literal["none","active_goal","saved_plan",
        "pending_clarification","tool_action"]
    reference: ReferenceProposal
    execution_scope: Literal["none","single_tool","first_step",
        "remaining_steps","all_steps"]
    effect_intent: Literal["none","read_only","mutation_requested"]
    explicit_constraints: list[ConstraintSpec]  # explicit only, <=16
    source_evidence: list[SourceSpan]           # <=12, current user message only
    clarification: ClarificationDecision
    ambiguity: Ambiguity
```

Implementation may use Pydantic with `extra="forbid"` and bounded field lengths. All typed enum labels above are semantic *proposals*, not verified tool names, permissions or proof of source binding. Schema validation and Host admission are separate operations.

### Evidence constraints
1. Exact source span matching occurs against the **current raw user content**; offset mismatch fails validation. A span proves the user wrote bytes/characters, *not* their meaning or authorization. No source span from model text, tool data or prior turns is authoritative for a new write.
2. `goal` can be null for continuation/status/cancel/clarify; for `goal_change.kind in {new_goal,add,revise}` in an understood action, retain v1's non-null goal requirement. Existing trusted goal versions are Host-owned.
3. `explicit_constraints` may contain only `source=explicit`. A negative user constraint is part of admission evidence and must never be silently dropped; ambiguity over “do not execute” fails closed.
4. All available authoritative plan IDs/revisions, pending tool names/required fields, and registered capabilities come from Host state, **not this schema**. Model-named tool IDs never create registry entries.
5. For a reply to pending clarification, `reference.kind=pending_slot` and `route_target=pending_clarification` may accompany `agent_loop`; Host only fills the already stored, single pending action and its allowed field.

## 2. Primary route combination table

| primary_route | route_target | scope | effect_intent | obligatory constraints |
|---|---|---|---|---|
| respond | none / active_goal | none | none | no tool or persistent plan admitted; optional goal change is proposal, not automatically saved |
| clarify | none / active_goal / saved_plan / pending_clarification / tool_action | none | none | clarification.required=true, non-none reason, nonempty question; no tools |
| agent_loop | tool_action / none / pending_clarification | single_tool / none | none / read_only / mutation_requested | pending_slot only when Host has compatible bound pending action; tool scope must be Host checked |
| plan_create | none / saved_plan | none | mutation_requested | explicit request to persist formal plan; no tool execution this turn; existing saved plan => conflict, not overwrite |
| plan_execute_first | saved_plan | first_step | read_only / mutation_requested | Host checkpoint + explicit current-turn execution; exactly stored step 1, never next pending |
| plan_resume | saved_plan | remaining_steps / all_steps | read_only / mutation_requested | Host checkpoint, authorized pending scope, cannot replay completed steps |
| plan_revise | saved_plan | none | mutation_requested | single pending bound step plus source-grounded old/new args; no tool call |
| cancel | none / active_goal / saved_plan / pending_clarification | none | none | cancellation of pending action/request; persisted cancellation, if later supported, requires separate explicit Host permission |

Important: `plan_create` is a durable *plan record* write, not a general tool write; `mutation_requested` is not permission. Current S25-02 can create only its existing supported formal-plan representation. `plan_resume` with an already fully completed plan must become a no-op response, not fallback normal tools.

**Invalid combinations:** unlisted target/scope, `respond` + `mutation_requested`, `clarify` with tool scope, `plan_revise` + read_only, `plan_create` + execution scope, `plan_execute_first` + remaining_steps, `pending_slot` without a Host-bound pending action, any route with conflicting constraints, and any `ambiguity.state!=clear` proposing an effect. Validation rejects these before any tool is exposed.

### Ambiguity outcome
- `clear`: eligible for Host admission, never automatic permission.
- `needs_disambiguation`: Host emits only a bounded clarification; no write or tool call. Persist pending question only if its referent/owner is verified.
- `unreliable` or schema-invalid/unavailable model: Host returns typed unresolved/provider error; zero tool calls, zero new plan/task writes, no invented confirmation. Do not downgrade a failed plan action into an ordinary effectful loop.

## 3. Deterministic Host admission (ordered)

0. **Owner / concurrency / idempotency**: validate conversation access, unique request ID, active Turn lock. Reject invalid requests without model authority.
1. **Trusted state**: read GoalStore confirmed versions, PlanStore snapshot/revision and pending_action with original tool/argument provenance. A malformed checkpoint is a refusal, never a model regeneration target.
2. **One semantic proposal**: pass only bounded trusted context. Identity of saved state remains Host metadata; observed model response is untrusted.
3. **Contract validation**: schema + combination table + exact current-input evidence, no conflicts with negative constraints. Ambiguous or invalid cannot become executable.
4. **Resolve references**: no saved plan for plan_resume => missing-plan clarification; stale step/revision => reject; pending slot only against original stored pending tool/field; unregistered capability => refusal.
5. **Host permission**: enforce no-write without explicit current request, read_only scope, Tool Schema and current/pending-original value provenance. An extra model review may *narrow* scope or request clarification, never promote text-only to a write.
6. **Admit exactly one route**: `respond | clarify | ordinary_loop | create_pending_plan | revise_pending_plan | execute_saved_first | execute_saved_remaining | cancel_no_side_effect | reject`.
7. **Execute existing path**: no new tool API. Host plan control only for the admitted saved-plan route; ordinary action gets `plan_control=None` even if a checkpoint exists.
8. **Verify/commit**: bound Observation changes step status; Turn/assistant/plan local finalization atomic per current boundaries; external tool effects not falsely called exactly-once.

### Host admission response shape
```
AdmittedTurnRoute(
  kind: enum,                    # from step 6
  rejection_code: enum | null,   # stable reason; no user secrets
  checkpoint_revision: int | null,  # Host-loaded value
  validated_binding: object | null, # Host-built, not model supplied
  allowed_tool_scope: list[str],    # Host registry intersection
  execution_mode: respond_only | read_only | execute
)
```
Only the Host creates this. A `clarify` or `reject` must have `allowed_tool_scope=[]`, and no side effects. A `respond` must use `respond_only`. An `ordinary_loop` can use read_only tools only after validated read-only source intent, or write tools only with explicit write permission.

### Permission lattice
`no_effect < read_only < write_requested` is **not a chain of automatic promotions**. Semantic intent is a ceiling bounded by Host rules. A second classifier cannot turn `respond_only` into any write permission. Read-only rescue after classification disagreement is permitted **only** if it is provably supported by the original user's explicit tool request, and receives a newly calculated Host admission decision rather than mutating a prior decision in place. Conflicting proposals without proof => clarification.

## 4. Existing v1 contract compatibility

1. Keep `UnderstandingResult` (`s25-01-v1`), `/understanding`, its validation, GoalStore version semantics and public API unchanged during M1/M2.
2. Provide future **versioned V2 producer** over the same trusted Understanding context. Do not derive a supposed V2 route solely from v1 `change.kind`: `revise` can refer to the goal or a saved plan and `continue` lacks execution scope.
3. During shadow mode both v1 and V2 may be invoked for comparison but **only existing v1 path** controls execution. Record V2 proposed route, Host would-admit/deny and reason without any V2 persistence or tool call. No hidden execution.
4. No fallback that treats V2 parse failure as `agent_loop`. Under actual cutover, fail closed and provide a clear error or clarification; do not silently let legacy classifiers regain control.
5. Preserve v1 user-facing API serialization and existing plan checkpoint format until compatibility tests show a safe migration. Existing stored checkpoints must restore without migration.
6. Explicit `goal_confirmation` is an out-of-band typed Host command with version validation; it does not need reclassification as a fresh user semantic action.
