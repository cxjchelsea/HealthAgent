## 3. 发现项与严重度

### P0-01：工具名级别错误消除，存在错误完成的可信性风险

`agent/loop.py` 的 `_tools()` 里：
```python
if result["ok"]:
    unresolved_failures = [item for item in unresolved_failures if item != name]
elif name not in unresolved_failures:
    unresolved_failures.append(name)
```
失败与修复按 **name** 而不是 action/argument/goal/plan-step/evidence 关联。假设 `calculate(8*8)` 失败、随后 `calculate(2+2)` 成功，即使原目标仍失败，工具级失败集合也被清空，而没有 pending plan 时模型 final 可令 `status=completed`。这是静态代码证明的风险，不声称已由真实 Qwen 复现。

**阻塞原因**：直接违反 S25-02 最小可信完成原则。建议 **最小定向整改**：未消除失败按 action identity（至少工具+参数）和绑定 Goal/Step 的可用程度区分，只有有证据的替代动作或原动作成功才消除；无足够目标绑定时保守输出 partial，并在 S25-03/08 深化为权威证据。覆盖无关同名成功、真正重试成功、有效替代工具成功以及普通对话。

### P1-01：澄清可跨一轮传递，但不是完整目标续接

`Turn.failure_code=needs_input` 标记最后的 `partial` 助手消息；`build_context` 只恢复当前消息预算容纳的那条问句。没有结构化 pending Goal、缺失 Slot、稳定澄清 ID 或目标版本；当上下文预算挤掉关联目标、连续多次追问或更换主题时，不能保证正确续接。**本轮范围**：补验证断言，不在 S25-02 偷做 S25-01/03/09 完整管理。

### P1-02：部分逻辑终态仍无可信执行入口

设计描述了 Pause/Denied/Cancel/Approval 等，但 PR #18 只补齐 Clarify；`AgentLoop` 没有服务端取消协调信号和逐动作检查，也没有持久审批 Authority。建议明确 **S25-02 只保留最小可执行停止/拒绝控制**，审批签发归 S25-12，用户控制 API 归 S25-16，Crash-safe 归 S25-11。是否要求最小取消阻断在 S25-02 Step 4 完成前落地，应以现有实际工具副作用风险评审决定；不能把按钮“停止等待”记为已取消服务端动作。

### P1-03：预算不完整

存在决策次数上限和单批 4 工具上限，尚无统一 per-turn 工具总次数、墙钟耗时、Token/成本预算及可恢复耗尽状态。S25-02 应最低保证有界、可解释的运行停止，增强预算治理归 S25-15；不强制提前实现成本计量平台。

### P1-04：旧关键词语义旁路未清理

`AgentLoop.run` 仍有算术正则更正、记忆关键词直查和“继续执行剩余步骤”的确定性捷径。可暂时作为兼容层保留，但这不是 S25-01 模型驱动 Understanding 的替代品，也不能作为陌生任务通用性达标证据。需设定 S25-01 集成后的退出计划，避免两套理解器长期并存。

### P1-05：真实 Agent 自主能力未验收
