## 一、架构事实与问题边界

1. `agent/understanding.py:UnderstandingResult` 为 S25-01 目标/变更/澄清结果（`s25-01-v1`），不能独立表达完整 saved-plan action、作用域与步骤参数。不得假设其已实现统一 M5 Route。
2. `agent/route_shadow.py:ShadowRoute`（`s25-route-v2`）具 `primary_route`、`route_target`、`execution_scope`、`effect_intent`、引文/引用/澄清/goal 信息及互斥组合校验；但这是 Shadow 诊断契约，**不含可供生产 Host 使用的完整计划执行参数和权限证明**，不能直接把实例送入 invoker。
3. `agent/route_semantic_hierarchical.py:PlanActionDecision` 已把 create/execute_first/resume/edit/cancel/uncertain 分为互斥的语义判断；分类器属于可复用的诊断思路，并未证实已经是正式 API 的单一主提案。
4. `agent/route_admission_m3.py:decide_admission` 仅给 `candidate_execute` 且 `execution_authorized=False`；其 `PreTurnFacts` 大量 authority 标志必须从可信 Host 状态计算，不能由模型填写。
5. `apps/api/main.py` 仍可分别调用取消、计划意图、步骤修订、通用 Understanding、待补参数/只读澄清、计划来源、执行授权与范围等审查。第 349 行和第 631 行通过 `reviewed_plan_intent or ...` 已有复用；**调用点不是实际运行次数字段**。M5 应度量具体执行轨迹并减少“第二个主意图裁判”，而不删除审计和授权。

## 二、目标架构与明确所有权

```text
HTTP 入站 + 身份/幂等 Turn 创建
    │
    ▼
CapturedTurn / PreturnSnapshot (Host 真实身份、plan revision、pending、权限源)
    │
    ▼
PrimarySemanticProposal v1 (本轮一次主语义解释；仅描述用户想做什么)
    │   ├─ typed: route、scope、reference、clarification、goal change
    │   ├─ source: 当前原文引文及唯一位置；模型不可伪造 Host 存在事实
    │   └─ operation payload: 操作级候选参数，不是调用工具的许可
    ▼
Host Source Binder + Schema Validator (确定性)
    │   ├─ 可选针对性语义修复：只修“缺失/歧义”的指定字段
    │   └─ 禁止修复模型重新选择主 route、提升权限或放大 scope
    ▼
Host Admission (身份 / 当前请求 / checkpoint / pending / schema / effect)
    │  deny | clarify | noop | candidate_execute
    ▼
Final Invoker Guard + Existing Domain Components
    │  PlanStore/CAS/Claim, DispatchJournal, Tool allowlist, AgentLoop
    ▼
Atomic DB Finalization + Observation
```

**单一主语义所有者 ≠ 单次全部 LLM HTTP 调用。** 必要的细节抽取、反证或格式修复允许发生，但必须窄范围、可观测、不可变更主路线，失败时 fail-closed。基线与改后分别计算 `primary_calls`、`bounded_repair_calls`、`security_review_calls` 和总 provider HTTP attempts。对执行写权限与危险工具必须维持独立 Host 验证；安全性不以模型自我声明为准。

## 三、建议的接口合同（设计提议，非现有代码）

```python
# agent/route_primary_m5.py
class PrimarySemanticProposal(BaseModel):
    schema_version: Literal["s25-m5-primary-v1"]
    route: Literal["respond", "clarify", "agent_loop", "plan_create",
                   "plan_execute_first", "plan_resume", "plan_revise",
                   "plan_cancel", "cancel"]
    target: Literal["none", "active_goal", "saved_plan",
                    "pending_clarification", "tool_action"]
    scope: Literal["none", "single_tool", "first_step",
                   "remaining_steps", "all_steps"]
    effect_intent: Literal["none", "read_only", "mutation_requested"]
    ambiguity: Literal["clear", "needs_disambiguation", "unreliable"]
    evidence: list[EvidenceSpan]
    reference: ShadowReference
    clarification: ShadowClarification
    goal: GoalSpec | None
    goal_change: GoalChangeProposal | None
    # None or one route-specific typed proposal.
    operation: OperationProposal | None

# operation: discriminated union with exact route-tag:
# plan_create -> bounded ordered ProposedStep(goal, tool_name, arguments, evidence)
# plan_revise -> ProposedRevision(step_id, expected_old_args, new_args, evidence)
# agent_loop -> Optional ProposedToolAction(name,args,evidence), with Host schema gate
# plan_execute_first / plan_resume / plan_cancel -> explicit source reference/scope
# pending -> reply/source binding, never a guessed pending ID
# respond / clarify -> no executable operation
```

建议从 `ShadowRoute` 组合规则、`UnderstandingResult` 的 Goal 类型和 `PlanActionDecision` 的互斥行为中复用约束，而非直接复制一套相互竞争的业务分类器。避免破坏旧 JSON：用新版本显式类型转换，不在原 `s25-route-v2` 默默添加生产授权字段。

`PrimarySemanticService.propose(captured, message, history)->PrimarySemanticProposal` 负责 **仅一次 route 选择**；输入 Host Snapshot 时仅传最小只读摘要/opaque IDs，不传其他用户信息及鉴权凭据。服务不访问 DB，不调用工具，不写状态。

`HostProposalBinder.bind(proposal, captured, current_message, tool_registry)->BoundIntent | TypedRefusal` 负责校验原文偏移与文本、step ordinal 唯一性、plan revision、pending source、工具注册/参数 schema、适用用户/会话。对引用不确定的模型输出不得修复为“已授权”。

`AdmissionGateway.decide(bound, trusted_preturn_facts, policy)->AdmissionDecision` 只能产出候选效果，必要时继续现有 domain-specific `admit_guarded_plan_*`；`candidate_execute` 必须经过既有 Final Invoker Guard、计划 CAS、Claim 和 DispatchJournal。若本轮路由不支持，**在任何状态副作用之前**根据固定配置选择 legacy 或明确拒绝；不得失败后重新调用另一条分派路径。

## 五、实现顺序：一个集中工作包中的四个连续动作

1. **事实基线与调用计量**：main 精确 SHA；分别在 structured/guarded 与 direct/legacy 路径收集真实调用明细、拒绝原因、tool traces、checkpoint/Claim/Dispatch 读回。原 M4 对照 `7+10+7` 是 baseline 线索，不可推断每个调用属于哪种 reviewer。
2. **并行但无副作用的主提案验证**：以非执行 instrument/shadow 证明 proposal 对全部既有意图和未见表达的稳定性；每个样本必须将来源位置绑定及权限拒绝归因单独评分，不得将 `compatible` 计为 exact。
3. **单一真实分派、逐场景切入**：守住 `route_admission_mode=legacy` 默认；在 guarded 中先 plan_create 与 read-only、再 first/resume、revision/cancel、pending/unsupported。切换前已有可运行的前置安全门，必要时不支持的路由在 Turn/能力调用前选好 legacy，不能双执行。
4. **去重与集中验收**：清理已经不在主链调用的分类器，保留兼容/诊断所需公共类型；集中真实 Qwen3 AB/BA + CI Postgres 并发/崩溃/幂等/不同用户/计划回滚与读回；独立 Step 5/6 审查之后再提交 PR。不得越过授权合并。

## 六、验收门槛

- **P0 安全**：零未授权工具、零 plan-only 提前执行、零 FIRST 越界、零跨用户串扰/不确定执行自动重放、零 Checkpoint CAS/Claim 失效。原 M4 数据恢复和未解决 Dispatch fence 必须有效。
- **行为**：plan_create / revise / first / resume / cancel、standalone tool、pending follow-up、unsupported、ambiguous/negative constraints，以及重复请求、竞争、错误降级等用一致的语义判定矩阵比较。强要求具体工具名/参数、执行次数、状态与已保存 plan revision 一致；文本 HTTP 200 不是成功条件。
- **主语义单一性**：一次 Turn 最多产生一个 primary route decision；任何进一步模型调用有分类、理由及次数；不会让它覆盖既选定的主动作。至少以 CI trace 断言，有真正业务路径证据。
- **调用与延迟**：输出按操作类型/成功与失败分类的 per-Turn provider HTTP attempts、真实 Qwen3 平均/P50/P95 和总功能通过率；与冻结基线做 AB/BA 对照。期望典型重复语义路由明显减少独立模型判断；不设未经测量的固定减耗百分比，不能删安全检查换性能。
- **安全范围/默认**：Shadow 仍诊断-only；legacy 默认，M5 只在显式 guarded 内验证；不存在通用外部副作用 exactly-once 声明。
- **验收证据**：精确 HEAD CI、独立真实模型、DB 物理读回和最终审查。

## 七、独立设计审查：发现与修改要求

**结论：PASS WITH AMENDMENTS；可以进入定向接口设计验证，但不直接批准全面替换。**

1. **高优先级 A — 解决 Proposal 与真实工具参数断层**：现有 `ShadowRoute` 无完整可执行 payload；必须定义 `OperationProposal` 的各路由严格 Pydantic union、负向约束和长度限制、来源证据，并由 Host 二次绑定。未完成前禁止用 ShadowRoute 直接接线到执行。
2. **高优先级 B — 区分单一语义决策与安全复核**：`review_plan_execution_authorization` 不能被无条件删除。必须提供由当前用户原文、计划快照、CAS/Claim/允许工具范围独立校验的替代控制，尤其是模糊 resume 与 first 的作用域。
3. **高优先级 C — 路由切换的事前选择证明**：M5 不能从一次有副作用的 guarded 执行失败后再试 legacy。必须对一次 Turn 只有一个 dispatcher 给出物理 E2E、crash/replay 证据。
4. **中优先级 D — 保证理解能力兼容**：M5 的 plan 优化不能破坏 S25-01 GoalSpec/Clarification 的跨轮目标理解，也不能让独立计算被错误吸附进旧计划。
5. **中优先级 E — 观测与成本分解**：已有 M4 `X-HealthAgent-Model-HTTP-Attempts` 仅计次数，不记录“哪个 classifier”；M5 第一动作先增加安全的分类汇总指标，避免“删了很多调用”的未经证实结论。
6. **中优先级 F — 不误用诊断结果**：M3 `candidate_execute` 永远 `execution_authorized=False`；新增真实 Host admissibility 需要独立正式事实，而不是 synthetic/后验 Shadow facts。

**设计准入门禁**：以上 A/B/C 的接口与审查样例必须完整；完成后才进行实现，不需要再次拆成 M5-A/M5-B/M5-C 五六层。

## 八、明确决策

- 建议启动 **M5 单工作包的设计接口验证**，保留默认 legacy 和现有 guarded M4 安全层。
- 此文档是可审查的设计基线，**未授权改变真实路由、删除分类器或合并 PR**。
- 若接口验证发现现有 M4 已经避免实际重复主分类，M5 应缩小为删除废弃分支 + 独立回归；不要为了实现“统一”重复搭建新 runtime。
