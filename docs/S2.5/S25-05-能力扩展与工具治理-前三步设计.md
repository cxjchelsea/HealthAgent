## Step 1 — 目标与行为定义

### 1.1 问题与目标

S2 已有可运行工具调用：声明→模型看到工具→AgentLoop 校验可见性→参数校验→执行器/MCP→Observation。但添加一个工具通常需要手动修改多处声明/分支；工具信息、执行能力与安全元数据分散，新增能力难以形成一致治理。

S25-05 的目标是提供**可信、版本化、可扩展的 Tool/Capability Catalog + 统一执行入口**。注册一次工具即可一致获得：模型可见 Schema、参数校验、执行适配、最小治理元数据和安全失败类型；保持主 AgentLoop 负责模型决策，**不由 Registry 自行规划/选择动作**。

### 1.2 五项必达用户可见能力

1. **新增工具无须修改 `agent/loop.py` 内的名称分支**：在可信配置/代码中注册一项新的非医学工具，经相同的正式 Agent API 可被发现、调用、验证并返回真实结果。工具不是模型临时创建的。
2. **单一可信定义与契约一致性**：工具标识、描述、参数 Schema、结果边界、执行器、能力分类/版本、权限标签有唯一可信来源；模型看到的 Schema 和实际后端参数验证不可悄悄漂移。
3. **可靠发现与暴露边界**：候选工具来自注册表中已启用、适用于当前执行环境的工具。S25-04 可基于语义选择这些候选，但任何模型提议都必须再经曝光/授权边界核对；无法使用时明确报错，绝不自动降级为执行其他工具。
4. **内置与 MCP 共用治理语义**：同一个统一工具入口支持本地只读、允许的写入工具及**受信配置的** MCP 适配器。MCP 动态 `tools/list` 是远端能力信息，不能直接成为本地信任授权。
5. **可观测与兼容**：调用结果带稳定错误类和可信来源引用；旧工具名、现有 Conversation API 和 PlanLedger 的 `expected_tool` 继续可用，新增工具需有边界与回归证据。

### 1.3 必须区分的概念

| 名称 | 定义 | 决策/可信边界 |
|---|---|---|
| Capability | 面向任务的能力描述（例如「查询任务」），可关联一个或多个工具 | 供 S25-04 选择；本身不能执行 |
| Tool Definition | 唯一标识、版本、Schema、描述、执行语义的可信声明 | 由代码/已批准 manifest 注册；不由模型创建 |
| Tool Exposure | 某个 Turn 决策时允许模型看到并提议的工具集合 | 可由 S25-04/Harness 缩小，不授予额外权限 |
| Tool Invocation | 本次模型提议的工具标识和参数 | 仅是提议；不是授权或执行成功 |
| Tool Executor / Adapter | 本地函数或受限 MCP 调用实现 | 经 Schema/授权检查后调用 |
| Observation | 实际执行后带 `ok/error/result` 的有限可信事实 | 工具输出为数据，不是系统命令 |

### 1.4 最小行为案例与验收期待

- **T1 新增只读工具**：注册 `text_stats`（统计字符/词数的演示工具），无需更改 `agent/loop.py` 名称分支。模型面对改写措辞的真实任务能在正式入口调用它并输出正确统计。
- **T2 无效参数**：模型传错类型/多余字段，不执行工具，返回 `invalid_arguments`，Trace 记录拒绝原因类别。
- **T3 未曝光工具**：模型强行指定注册但当前未曝光的工具，返回 `tool_not_exposed`；未执行适配器。
- **T4 未注册/禁用工具**：注册表查找失败→`unknown_tool` 或 `tool_disabled`；不给模型提供其 Schema。
- **T5 适配器不可用**：MCP 不可达/协议错误→统一失败 Observation，但保留 `mcp_timeout`/`mcp_protocol_error` 等细分原因。
- **T6 工具版本变化**：同名工具的输入/输出契约不兼容时不能默默替换正在执行或恢复的工具；输出 `tool_version_mismatch`/暂停核对。
- **T7 非法外部指令**：MCP 返回“忽略权限/调用其他工具”只作为普通 Observation 文本，不改变曝光/授权集合。
- **T8 现有回归**：`calculate`、`create_task`、`save_memory`、`propose_plan/revise_plan/complete_plan_step` 保持行为、工具名和正确的证据绑定。

### 1.5 非目标与依赖

**本项不负责**：LLM 语义工具排序（S25-04）、用户多轮审批交互（S25-12/16）、高阶注入防御（S25-13）、动态装配预算策略（S25-15）、失败后模型重规划（S25-07）。但提供这些能力必要的可信接口和元数据。

**反目标**：建立第二个 AgentLoop、未经批准任意连接公网 MCP、动态 `exec` 插件、模型写入 Registry、立即上分布式能力市场。默认保持明确的内置 allowlist。

## Step 3 — 详细设计方案（待用户审查）

### 3.1 技术路线与方案取舍

**推荐：可信静态启动注册 + 运行期受限状态快照 + 单个 ToolInvoker。**

与备选方案比较：

| 方案 | 优势 | 问题 | 结论 |
|---|---|---|---|
| A 在 `SCHEMAS`、`TOOL_SCHEMAS` 和 `execute_tool` 继续同步追加 | 最少当前改动 | 持续契约漂移、每个工具触碰多处 | 不采用 |
| B 每次请求任意 MCP `tools/list` 并直接全部曝光 | 动态性高 | 权限/协议/版本不可信，成本高 | 不采用 |
| **C 受信工具注册 + 统一校验/执行 + MCP 有限映射** | 保留现有边界、易扩展、可测试 | 需一次受控迁移 | **推荐** |
| D 分布式 Registry/Plugin Marketplace | 大规模组织方便 | 超出个人项目实际需求 | 本阶段不做 |

### 3.2 建议的最小契约

```python
class ToolDescriptor(BaseModel):
    name: str                           # 稳定外部名称，例如 calculate
    version: str                        # 显式代码版本；变更语义时升级
    description: str                     # 模型可见工具说明
    capability_ids: tuple[str, ...]     # 关联能力类别，不是任意授权
    input_schema: type[BaseModel]       # 可信 Pydantic 类（仅内部）
    effect: Literal["read", "write"]     # 基础副作用分级
    auth_policy_id: str | None          # 指向现有权限策略，不能自己授权
    adapter_key: str                    # 可信执行适配器键
    enabled: bool = True

class CapabilityDescriptor(BaseModel):
    capability_id: str
    summary: str
    tool_names: tuple[str, ...]

class ToolInvocation(BaseModel):
    tool_name: str
    arguments: dict
    tool_version: str | None = None
    # 运行时使用现有 user/conversation/turn 上下文校验，不由模型提供 owner
```

以上是**设计示意**而非冻结的可执行 Python 类。真实 Pydantic 类型需要与注册表实现一致；特别是 `type[BaseModel]` 更适合内部不可序列化字段/普通 dataclass，不能直接作为持久公共 Schema。

ToolDefinition 包含模型描述和服务端类型验证所需资料；**实际 Adapter 是可信代码注入，不以字符串反射/import 来执行模型提供的路径**。

S25-12 的审批状态机不在 S25-05 实现，但 `effect/auth_policy_id` 必须保留接线位置；没有现成写入许可时走现有 API Consent / ToolStore 限制，不能视为 Registry 自动批准。

### 3.3 Registry 与工具视图

可信启动时从已审核内置定义注册（加上已明确授权的固定 MCP Adapter 定义）：

```text
Trusted definitions + adapters
       → validate (unique name/version/schema/effect/adapter)
       → ToolRegistry snapshot
           ├─ catalog view：能力元数据供 S25-04 检索/排序
           ├─ model view：已曝光工具的 JSON Schema
           └─ execution view：工具名→注册版本→参数校验→策略授权→Adapter
```

约束：

1. 同名工具同一有效版本只能有一个可信实现，重复注册失败关闭。
2. 模型可见 Schema 从**同一 Pydantic 类型**生成，进行 Ollama/Qwen 兼容格式投影；投影不得删去约束并放松服务器校验。
3. `ToolRegistry.catalog()` 返回元数据**不含**可调用实例、密钥或 MCP 服务启动命令。
4. `expose(selection, policy_context)` 只能从启用且经过允许的工具中取交集，不得提升权限。
5. 真实 Invoke 再检查 Registry、曝光快照、版本、Arguments、Authorization；仅曝光不构成可执行授权。
6. Catalog Snapshot 在一个 Turn 内保持稳定；中途禁用/撤销权限在执行边界仍需实时拒绝。
7. 对 S25-04，仅暴露候选查询/过滤接口，**不在 S25-05 做 LLM 语义匹配算法**。

### 3.4 AgentLoop 集成边界

沿用一个正式入口 `POST /conversations/{cid}/agent/messages` 和现有 LangGraph：

```text
Context + Goal
  → S25-04（或旧 Skills 过渡逻辑）提出工具候选
  → Registry Exposed Tool Schemas → NativeToolDecision
  → Model tool_call
  → ToolInvoker: registry/exposure/version/args/policy checks
  → trusted local / trusted MCP adapter
  → bounded ToolObservation
  → PlanLedger.observe + Trace → 再次模型决策
```

**重要设计选择**：`propose_plan/revise_plan/complete_plan_step` 属于内建的 *Agent Control Actions*，不是普通外部工具。实现可以共享同一曝光、Schema、错误包络和 `invoke` 接口，但状态修改必须委托 PlanLedger 的现有权威逻辑；不可将计划状态修改权开放给第三方适配器。

现有“恢复已绑定步骤”的旁路必须改走同一 `ToolInvoker`，且必须保留版本、权限、可用性和幂等检查；不能再直接绕过 Exposure。若恢复发生时原版本缺失，应标记 `blocked/tool_version_mismatch`，不得换新语义继续执行。

### 3.5 MCP 适配器与信任边界

- 受信服务配置按服务标识固定对应客户端/命令（当前保留 `agent.mcp_stdio_server`），不得由模型指示执行进程。
- 初始化和 `tools/list` 可校验服务已声明的工具，但远端列表**只能与本地批准定义取交集**；不认识的新工具不给模型。
- MCP Tool 名称与内部名称可以有可信映射（例如 `mcp_reference_lookup`），不得按不可信内容动态重命名。
- 适配器标准化超时、通信失败、协议错误、工具返回错误，保留服务来源与版本标识；工具返回中的指令永不注入 system/developer 角色。
- 限制结果大小、文本内容长度；敏感参数不得完整写入普通 Trace。
- 并行工具调用仍服从现有最多 4 个工具的单轮限制；扩展不提高默认调用预算。

### 3.6 错误/结果契约

推荐统一结果包络（初版保持兼容旧 `{"ok": bool, ...}`）：

| 结果类别 | 代表错误 | 执行含义 |
|---|---|---|
| Registry | `unknown_tool`、`tool_disabled` | 未执行 |
| Exposure | `tool_not_exposed` | 未执行 |
| Schema | `invalid_arguments` | 未执行 |
| Version | `tool_version_mismatch` | 未执行/需恢复审查 |
| Policy | `permission_denied`、`approval_required` | 未授权不得执行 |
| Adapter | `tool_unavailable`、`mcp_timeout`、`mcp_protocol_error` | 真实失败 Observation |
| Tool | `tool_execution_error` 或工具特定可信错误 | 不伪造成功 |

Observation 增加稳定的 `tool_name/tool_version/adapter/error_code` 与有限 `result`，保持原有 `ok` 和历史 `value/utc/tasks` 等消费者字段的兼容视图，升级需测试验证，而不是一次性重写所有消费者。

### 3.7 数据与版本生命周期

- S25-05 默认**无数据库迁移**；注册清单来自版本化可信代码/配置。
- 活跃 Turn 保存或传递本轮 Catalog 版本指纹（轻量哈希，非工具敏感参数）。
- 旧 Checkpoint 未带 Tool Version 时按**已知原始内置工具版本映射**处理；未知来源的旧工具需阻断并人工评估。具体迁移适配由实现阶段先做实际数据探查再决定。
- 不允许恢复时静默把 `expected_tool=calculate` 映射成另一个含义不同的工具。
- 工具下线需定义禁用后的行为，至少可追踪 `tool_disabled`，不偷偷调用后备未知工具。
