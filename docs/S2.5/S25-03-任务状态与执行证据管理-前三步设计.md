## Step 1 — 目标能力定义

### 1.1 为什么需要 S25-03

当前已有会话 Turn、计划 Revision、Step ID、Checkpoint、工具调用 Trace 和基础成功证据，但它们不构成完整、**可独立证明的任务事实链**。用户曾遇到：步骤标记完成却不能在下一轮交付历史具体结果；恢复时出现无理由修订；工具失败但不清楚是哪次尝试及为何停止；计划完成与最终结果交付不一致。应把可靠的任务事实与模型生成的计划建议、回答文本严格分开。

**核心目标：**对每次通用 Agent 任务提供可持久化、可引用、可校验的 Goal → Plan Revision → Step → Action Attempt → Tool Observation → Artifact/Result → Task State 关系，支持跨轮读取和失效追踪。由确定性宿主负责标识、版本、状态变更与证据合法性；模型负责提出目标、行动和解释，不能自行宣布外部副作用已提交。

**边界：**S25-03 负责**记录与维护可信事实**；不是在本项中实现完整的 Planner（S25-06）、动态 Replanning（S25-07）、综合完成验证（S25-08）、真实中断恢复调度（S25-11）或新的审批机制（S25-12）。为这些能力预留契约，但避免提前实现其复杂策略。

### 1.2 用户可观察行为与场景

| ID | 场景 | 应观察到的行为 | 必须拒绝的错误行为 |
|---|---|---|---|
| TS01 | 模型制定计划并调用计算工具 | 生成稳定 Step ID 和 Attempt ID；Observation 成功后形成可引用结果；最终可展示数值 | 仅因模型说“完成”就写 completed |
| TS02 | 工具执行失败再修订 | 同一步可有多次 Attempt；失败及原因保留；新有效尝试不覆盖历史失败 | 用新结果改写旧 Observation |
| TS03 | 用户把已完成 8×8 更正为 9×9 | 保留旧 Step/证据历史但标为对新目标失效；新 Revision/Step 与新证据建立关联 | 删除历史证据或把旧数值用作新目标完成证明 |
| TS04 | 第一轮完成一步，第二轮继续 | 可读取历史步骤结果/证据引用，并只执行必要的剩余步骤 | 仅恢复 completed 标志却丢失结果 |
| TS05 | 已提交工具返回前连接中断 | Attempt 进入可辨识 unknown_outcome / reconciliation-needed，不能假装失败后安全重试 | 未核实直接重复持久写入 |
| TS06 | 工具返回含伪造指令 | Observation 保留数据与来源但不提升为系统命令或授权 | 执行“忽略规则”等工具文本 |
| TS07 | 不同用户/会话请求状态 | Owner 隔离；无权限不能读取状态、结果或引用 | 仅凭猜测 ID 读到其他人结果 |
| TS08 | 两个请求修改同一活跃任务 | 版本或原子条件阻止过期更新覆盖有效状态 | last-write-wins 静默丢进度 |
| TS09 | 计划修改只保留部分步骤 | preserved 的 Step/Evidence 引用不变；废止项仍可审计 | 重新编号已有步骤或无依据标 completed |
| TS10 | 任务失败、取消或 partial | 记录真实最终状态、终止原因与下一步，结果引用可查询 | HTTP 200 即视为全部目标完成 |
| TS11 | 工具结果过大或敏感 | 保留有界、安全的结构化投影及受控引用；原始敏感内容不默认落 Trace | 无上限将模型/工具响应全文存入计划快照 |
| TS12 | 历史旧格式 checkpoint | 仍能读取基础状态，旧结果标记 unavailable/not recorded，不伪造 Attempt | 读取旧数据时报错或伪造历史事实 |

**最关键的两个行为**：历史工具真实结果能跨轮被安全回放；失效完成证据不会再次成为现目标的完成凭据。第一项解决已见用户问题，第二项避免任务状态“看上去完成、实际错误”。

### 1.3 不变量（未来实现与验收必须遵守）

1. **证据的权威来源**是获准的实际 Tool Executor / Host Observation，而不是模型自述；任何写入、成功、完成均需可核验来源。
2. `goal_id`、`step_id`、`attempt_id`、`observation_id` 与 `artifact_id` 的权威值由 Host 生成并按作用域唯一；引用必须属于相同 Owner/Task。
3. **事件不可静默改写**：错误、失效和更正用新事件/版本表达；可在合法删除策略下安全擦除敏感载荷，但不重写历史成功为新事实。
4. `Step completed` 是由已验证 Observation 支撑的状态，不等于 Task completed，更不等于写操作确认完成。
5. `unknown_outcome` 不属于可直接重试的普通 failed；执行结果不明时不自动重复外部副作用。
6. 状态切换应有明确的旧状态、新状态、原因、来源和一致的 revision；不能发生 stale overwrite。
7. 对用户可展示的 Result 只来自受控、脱敏后的证据投影；不应通过模型“回忆”补造历史数据。
8. 同一 Turn 的必要状态/证据/消息终结写入应满足明确的事务一致性；对外部工具副作用不能声称跨数据库原子。
9. 数据大小、字段、保留期限与权限均受上限；不建立无限增长的通用原文日志库。

### 1.4 非目标

本项不建立 Scheduler、长期无人值守任务执行、跨节点分布式一致性、多 Agent 事件平台、完整审批 UI、复杂知识图谱/向量数据库，不替代既有 Trace、业务数据库或 LangGraph 本身。Observation 保存是**结果投影与引用**，不是重复整个工具输出。当前可以先用 SQLite 做功能和事务合同测试，PostgreSQL 并发需独立实测。

## Step 3 — 独立详细设计（供审查）

### 3.1 方案对照及推荐

| 路线 | 优点 | 风险 | 结论 |
|---|---|---|---|
| A. 继续把一切塞进 `conversation_plans.snapshot` | 修改少，易于 demo | 并发覆盖、结果越变越大、独立证据查询困难 | 不作为长期主路 |
| B. **现有 PlanLedger + 最小关系型证据表 + 轻量事件投影** | 可复用当前代码与事务，能查询证据和旧 Revision，易于测 | 一次数据库迁移，需要明确映射与兼容性 | **推荐** |
| C. 完整 Event Sourcing/Workflow Runtime | 重放丰富 | 引入额外运维和状态权威、过度设计 | 本轮不做 |
| D. 仅增加 Trace 日志 | 很快 | Trace 不是可靠执行权威，不解决历史结果引用 | 不选 |

**选 B，但应严格限制表数与字段规模**。建议先定义最小 `TaskRecord`、`StepRecord`、`AttemptRecord`、`ObservationRecord`，并复用 ConversationPlan 快照作为兼容读取；Artifact 首期只允许 Observation 的有界投影与可选引用，不强制独立大 Blob 表。审查通过后，实施可决定“表 + 关联 JSON”还是合并小型事件表，衡量迁移成本后再冻结 DDL。

### 3.2 统一语义与对象（设计候选）

**TaskRecord（持久任务）**
- `task_id`（Host UUID）、`owner_id`、`conversation_id`、`active_goal_ref`（未来 S25-01 GoalSpec 的受控引用）、`task_revision`、`state`、`created_at/updated_at`。
- `task_revision` 为存储版本，区别 `plan_revision`（计划结构版本）和 `goal_version`（语义目标版本）。
- 首版一个 Conversation 最多一个活跃 Task（与现有单 `ConversationPlan` 兼容）；多活跃任务属于后续扩展，不默认在本项完成。
- Task 与 ConversationTask（待办条目）**不相等**，命名不可混淆。

**PlanVersion / StepRecord**
- `plan_revision`：保留 PlanLedger 现有 revision；历史修订不覆盖。
- `step_id`：保留当前会话内递增且不复用语义；推荐增加内部 `step_ref=(task_id,step_id)`，不强迫前端改展示 ID。
- `goal_text`、`status`、`expected_tool`、`expected_arguments_digest`、`active_from_revision`、`inactive_from_revision`、`completion_evidence_ref`、`failure_reason`。
- 不默认原样复制敏感工具参数；是否需要执行重试参数，单独受控加密或安全字段投影。
- 修订保留未受影响完成步骤，受影响步骤标 **superseded** 且历史可查；不能修改原 Observation 的结果值。

**ActionAttempt（单次执行尝试）**
- `attempt_id`、`task_id`、`turn_id`、`step_ref?`、`tool_id/name/version`、`arguments_digest`、`idempotency_key?`、`state`、`started_at/finished_at`、`error_code?`、`observation_ref?`。
- 同一步可有多个 Attempt；无计划的直接工具调用也有 `step_ref=null`。
- Attempt status：`prepared / running / succeeded / failed / unknown_outcome / cancelled`；`unknown_outcome` 与普通失败不同。
- `idempotency_key` 对外部写操作不等于保证幂等；必须由对应工具适配器/对端真正支持或查证结果。

**ObservationRecord / EvidenceRef**
- `observation_id`、`attempt_id`、`source=approved_tool_executor`、`ok`、`error_code`、`observed_at`、`result_projection`、`projection_schema_version`、`payload_digest`、`sensitivity`、`trust_level=tool_data`、`artifact_refs`。
- `result_projection` 是受限、脱敏的**已观察结果**，如 `calculate 9*9 → 81`、MCP 来源与资料摘要；不得由模型凭空生成。
- 需要展示原始结果但已不可获取时，明确标记 `not_recorded`、`redacted` 或 `expired`，不生成虚构回放。
- `EvidenceRef` 包含 `task_id/step_id/attempt_id/observation_id/tool_identity/arguments_digest/plan_revision/evidence_status`，由 Host 验证引用有效及当前 Goal/Revision 是否仍适用。
- Artifact 首版可记录 `artifact_id,type,content_digest,size,storage_ref?` 元信息；正文暂不默认持久化，未来报告文件、RAG 文档受控外置存储。

**StateTransition（记录状态依据，非任意日志）**
- `transition_id`、`entity_ref`、`from/to`、`reason_code`、`caused_by_attempt/observation/turn`、`expected_revision`、`resulting_revision`、`timestamp`。
- 可以用小型 append-only transition 表或随 Step/Attempt 事务保存的事件记录；**无需**完整 Event Sourcing。
- 过渡事件与业务状态在同一 DB 事务提交；追踪信息是投影，不替代数据库状态权威。

### 3.3 状态机建议与职责区分

| 对象 | 建议状态 | 谁能改变 | 关键规则 |
|---|---|---|---|
| Task | `active / waiting_user / partial / completed / failed / cancelled` | Host 根据已验证目标状态及用户授权 | 不允许模型仅凭自然语言置 completed |
| Step | `pending / running / completed / failed / blocked / skipped / superseded` | Host 依据 PlanLedger/Observation/Goal 修订 | completed 必须有关联成功证据；superseded 不代表证据被删除 |
| Attempt | `prepared / running / succeeded / failed / unknown_outcome / cancelled` | Tool Invocation Host | 对外部副作用结果不明需待核验 |
| Observation | immutable / redacted / expired | 可信 Executor 负责创建，隐私/保留策略负责限制载荷 | 不能被模型改写；状态变迁不改变历史 ok |
| Plan Revision | 单调递增整数 | PlanLedger + 原子提交 | 旧版本可查询，不允许 stale update 覆盖 |

**关键注意：** `failed` Attempt 不应必然把 Step 永久置 `failed`；Step 可在错误恢复机制允许后重新尝试。相反，一次成功 Attempt 也不自动证明整个 Task 完成。Task/Step/Attempt 之间不可混用同一状态语义。

**已完成证据的失效**：新目标或 Plan 修订可使 EvidenceRef 对新目标不再适用（`inactive/superseded`），但原 Observation 仍证明旧工具曾给出该结果。失效不是数据删除。

### 3.4 可信事实写入与正式 Agent 执行接线

设计中的标准路径（非新的执行入口）：

```text
POST /conversations/{cid}/agent/messages
  -> Owner + Turn Guard + Request ID
  -> Context/已确认 Goal 或旧 checkpoint
  -> AgentLoop（现有 LangGraph）
       -> model decision proposes Tool Call
       -> allowlist/schema/policy validation
       -> create Attempt (Host-assigned)
       -> execute tool once / observe verified result
       -> persist Observation projection + evidence association
       -> PlanLedger.observe / conditional Step transition
       -> feed lower-trust Observation to model
  -> Finalization with verified plan/task state
  -> atomic DB commit: Turn + Message + Plan Snapshot + Evidence/State
  -> Response/Trace references
```

**必须处理的真实实现张力**：现有 AgentLoop 在事务外调用模型和 Tool Executor；某些持久工具可能在最终消息提交前产生副作用。因此不能假定“最终同库原子提交”能包含所有外部副作用。首轮实现应优先保证只读工具结果的可靠落库、已有任务/记忆写操作权限保持不变；外部写操作要通过有状态 Attempt 和幂等/结果核验围栏处理，并由 S25-11/12 深化。

**建议的持久化策略**：
1. Tool Call 前生成 Host attempt ID，并记录准备状态；明确崩溃窗口。
2. 调用 Tool Executor；收到结构化结果，严格校验、脱敏并生成 Observation + EvidenceRef。
3. 在数据库允许的事务边界内一致更新 Attempt、Step/Plan、Checkpoint、必要状态转移和 Turn/Message；不将不可信工具全文直接插入 system prompt。
4. 工具已产生副作用但数据库提交失败时，该 Attempt 在恢复中视作结果不明，必须核验后才允许再次执行。
5. 允许已知结果的只读工具产生缓存/重算，但应保留引用与版本语义，不掩盖真正执行发生的次数。
6. 容错与性能需要基准数据支持；不为每个 token 写数据库。

### 3.5 数据存储选型及兼容迁移

**推荐：PostgreSQL/SQLite 共用 SQLAlchemy + Alembic 迁移，最小关系约束，必要列以 JSON 保存有界投影。**

待实现审查时确定具体 DDL，设计草案：
- `agent_tasks`：Task 主记录及 revision / owner / conversation。
- `agent_step_records`：Step ID、版本、生效区间、完成证据引用。
- `agent_action_attempts`：工具调用及结果权威状态。
- `agent_observations`：受限投影、摘要引用和来源。
- `agent_state_transitions`：按需小型状态变更审计；首个实现可暂与其他表合并，避免不必要建表。

**兼容规则**：
- 现有 `conversation_plans.snapshot` 继续可读取；设计 `schema_version=1`（旧）、`schema_version=2`（新）区分；旧 snapshot 无版本时按 v1 处理。
- 旧 completed Step 可保留 `evidence_tool` 与 completed 状态，但必须标记 `legacy_evidence_unresolved`，不可伪造新的 ObservationRecord。
- 迁移采用 **非破坏性新表/新字段**，不批量覆盖旧计划、不清空原 Step ID；部署后验证升级可重复，必要时可以回退新功能读取。
- 新旧读取双轨只允许一个权威写入源：若一段过渡期 dual-write，必须定义 commit 顺序和失败一致性；优先设计单一事务统一持久化，旧快照作为兼容投影。
- `Task` 与 `ConversationTask` 命名/数据库表严格隔离，避免业务待办项污染 Agent 执行身份。
- 数据保留应与用户所有权及删除路径一致；敏感投影不能默认长期无限保留。

### 3.6 版本、并发与故障边界

- `task_revision` 和 `plan_revision` 分开：Task CAS 管执行状态写入并发；Plan Revision 管计划内容修订；GoalVersion 管用户目标变化。
- 必须实现 `UPDATE ... WHERE revision=:expected` 或同等级锁/原子条件，并测试两请求竞争；仅依赖 Python 内存锁不足以覆盖多 worker。
- 已有同会话 active Turn guard 必须保持，不可为提高吞吐绕开。
- 故障类型分别测试：Tool 参数无效、成功 Observation 缺失、观察结果投影失败、DB 提交失败、Turn interrupted、模型最终响应失败、未知副作用结果。
- 失败时状态必须说明是真实失败、仍在执行、无法确认结果还是等待用户；不能将 503 统一解释为“工具未执行”。
- 一切读取 Evidence/Artifact 的 API 必须依据 Conversation Owner + Task 所属关系二次检验；即使引用 ID 合法也不得跨用户查阅。
- 工具输出做数据而非指令；摘要生成若使用模型，只能作为辅助文本，结构化原始可信投影仍来自适配器。

### 3.7 对外读取与展示接口（候选）

保留现有 POST Message 响应；建议在原有字段的兼容方式下新增：
- `task_id`、`task_revision`；
- 每 Step 的 `status`、`evidence_ref`、`result_availability`；
- Trace 记录 `attempt_id`、`observation_ref` 和 `transition_reason`（脱敏）。
- 可选只读 `GET /conversations/{cid}/agent/tasks/{task_id}` 和 `.../evidence/{observation_id}`，只有必要时才开接口。优先通过现有 Conversation API 暴露足够的结果引用，避免大规模扩展外部 API。

不在 S25-03 改写 UI 的全部 Trace 体验（属于 S25-17），但当前用户应能看见哪步有可靠证据、历史结果是否可用。

### 3.8 最小跨能力契约

| 邻近能力 | S25-03 提供 | 不越界实现 |
|---|---|---|
| S25-01 Understanding | Host 分配的 `task_id` / `goal_ref`、可信当前状态摘要 | 不让模型直接写权限或 Task 状态 |
| S25-02 Agent Loop | Attempt/Observation API、Step/Task 状态转换、ResultRefs | 不新建另一条 Agent Loop |
| S25-04/05 Tool Selection/Registry | tool_id/version、已批准 schema 和权限元数据引用 | 不负责模型选工具策略 |

| S25-08 Finalization | 已验证结果与缺口、目标版本关联 | 不由证据存储层生成未经验证的最终目标成功声明 |

### 3.9 审查后 Step 4～6 的建议验收设计（本次不执行）

**Step 4 实现建议：**
- Slice A：以只读 `calculate` 和 MCP 为起点，落地 Attempt/Observation/Step Evidence，保持旧 API 响应兼容；一次完整 E2E 可取回 8×8 结果。

- 不应只提交合同类、数据库表和模拟数据后即标“Agent 证据管理完成”；所有切片必须接正式主链。

**Step 5 自动化与真实模型证据：**
1. `Goal → Plan → 2 Attempts (fail/success) → 1 verified observation → completed step`；
2. 跨轮续做后历史 ResultProjection 仍可读取，不需要模型编造；
3. `revise_plan` 保留完成步骤、废止旧有效性且 stable ID 不复用；
4. Tool success 但没有对应参数/Step 匹配，不能写 Step completed；
5. 两请求 stale revision，CAS 拒绝、无静默覆盖；
6. 写入原子性与注入异常，Turn/Message/Plan/Observation 不产生不一致成功状态；
7. legacy checkpoint 完整可读，历史结果标 unknown/not recorded；
8. Owner A 的 Observation，Owner B 查询拒绝；
9. 受限敏感投影、超大输出、恶意工具文本不进入权威执行指令；
10. 真实 Qwen3:14b 经过正式 API 完成两轮多工具任务，核查 Observation ID、结果回放和状态引用一致；该结果需单独标注为 REAL_MODEL，不以 Fake Provider 代替。

### 3.10 仍需用户评审的关键设计决定

1. **状态粒度**：接受 Task、Step、Attempt 三层状态，Observation immutable，而不是简单为 PlanLedger 扩几个枚举吗？推荐接受。
